# ZJdesk

C++ / Qt 跨平台协作工作台，目标平台为 Windows 11 x64 与 Ubuntu 22.04 x64。
本项目沿用 MeetScope 的产品方向，以 ZJdesk 为工程名，按可验证的小版本持续开发。

## 启动后在主界面验证对端 IP

客户端直接显示主界面，协作空间的启动卡片只保留一个对端 IPv4 输入框和一个「连接服务」按钮（服务地址由验证自动设置，昵称在页头填写）：Windows 填 Linux IP，Linux 填 Windows IP，本机地址自动选择。验证通过后才出现「远程控制」按钮，点击它才发起远控，无需输入校验码。对端 IP 由随程序附带的小脚本给出：Windows 双击 `bin\tools\ip-info.cmd`，Linux 执行 `sh bin/tools/ip-info.sh`，脚本只输出「同局域网」「不同局域网」两个地址，照抄其一即可；空输入或验证失败会标红。修改地址会断开当前会话并要求重新验证；上次输入会保留，每次启动仍需验证。Linux 客户端自动提供双方共用的信令服务，默认端口 `8765`。

Windows 可双击 `直接启动.bat` 打开本机已部署的客户端。当前开发环境的 `构建启动.bat` 通过 SSH 同步、构建并启动双端，优先选择可用的局域网地址，也支持通过 Tailscale 跨网连接；跨网时两端 Tailscale 须在线。界面仍需双方验证对端 IP。新用户的完整操作及失败处理见 [启动网络验证](docs/startup-network.md)。

## 当前版本：IP 配对远控与四人会议

已实现：

- Qt Widgets 工作台：协作空间用于远程控制，视频会议页面提供会议和屏幕共享，另有运行诊断页面。
- 独立 WebSocket 信令服务，会议房间最多四人、协作房间最多两人；协作与会议按类型隔离，即使房间码相同也不会互通，同一客户端只能加入一个房间。
- 最多四人的局域网视频会议：入会自动连接、摄像头 / 麦克风 / 扬声器选择、各成员画面、静音和隐藏画面；共享一次摄像头采集并混音播放。会议支持一人向其余三人共享屏幕、多人同步标注，以及共享者授权后在参会者间切换当前桌面的控制权。
- 入会、等待成员、对方加入 / 离开、取消连接、错误反馈与手动重新入会。
- offer / answer / ICE 转发、房间隔离、版本化 JSON 协议及消息大小限制。
- 有界事件日志、JSONL 报告导出，以及远控授权与代次校验的核心逻辑。
- CMake / Ninja 构建、Qt Test / CTest 测试和 Windows 本地部署。
- 可选启用 GStreamer 1.26.11，枚举摄像头、音频输入与输出设备。
- 会议帧交接为本机及每位远端保留最新画面并限制待处理通知数量。界面不提供独立本地预览或视频测试源，合成测试源仅用于媒体回归。
- 音频测试源和低音量测试音。
- 摄像头从设备公布的最高分辨率及对应最高帧率开始，依据处理速度优先降低帧率，再降低分辨率，稳定后逐级恢复。
- 共享主屏幕采用 WebRTC / VP9 4:4:4 传输，保留细字和彩色细线；会议中其余成员自动接收，支持画笔、圆圈、箭头及共享者真实桌面的透明标注层，可停止、重开或交换共享方。
- 屏幕共享从主屏幕原始像素尺寸开始，自动帧率上限取双方主屏幕刷新率的较低值（最高 240 fps），依据实际编码、接收和显示速度逐档调整；降至 24 fps 仍持续落后时才降低分辨率，仅最低尺寸保留更低帧率。
- 降低帧率时保留文字画面码率，逐级试探恢复；自动目标最高 240 fps，实际效果以两端硬件、桌面和网络测量为准。
- 显示真实编码 / 接收 / 绘制帧率，区分目标参数与实际速度。
- 跨机回归记录键鼠注入确认、画面反馈、RTP 收发 / 丢包与实际带宽；接收缓冲保留实测稳定的 200 ms 默认值。
- 启用 RTP 丢包反馈 / 重传，丢包后请求关键帧并暂停依赖损坏参考帧的解码，避免持续花屏。
- Windows / Linux 启动脚本各打开一个客户端；未指定服务器时在后台启动信令服务。
- Windows 和 Linux 各自验证对端 IP 后可发起远控；被控方可在设置中选择是否需要再次点击允许。
- WebRTC DataChannel 传输授权和键鼠输入；按被控方设置手动确认或自动授权后，Windows 使用 SendInput、Linux X11 使用 XTest 执行。
- 远控授权期间，Windows 与 Linux 可双向复制文件 / 文件夹，传输完成后直接在目标电脑粘贴。
- 点击“放大画面”全屏查看并控制，放大时隐藏本机校验码及“缩小”按钮，按 Esc 恢复原窗口。
- 支持点击、移动、拖动、滚轮和常用键盘操作；拒绝、撤销、失焦和退会释放本程序按下的键鼠。
- 拖拽按 8 ms 节奏合并发送最新位置，保留末次移动；被控端回传光标形状，控制端在画面内使用本地系统光标即时响应移动，实际输入和窗口内容仍需网络传输。

双向摄像头和语音已接入独立 WebRTC 会话，使用方法与验证边界见 [视频会议](docs/video-conference.md)。

会议中的共享屏幕、本机和各远端摄像头画面均可点击右上角“放大”单独查看；点击“缩小”或按 Esc 恢复原布局。
Windows 被控后端已实现，真实键鼠和持续画质 / 帧率验收状态见 [Windows 被控验证](docs/validation-windows-host-20261103.md)；自动重连尚未实现。
两端验证对端 IP 并连接同一新版信令服务，控制方点击「远程控制」，按被控方的二次验证设置自动授权或等待允许后连接桌面。
点击“结束控制”会解除双方远控配对，停止桌面传输并清理授权；两端保留在线状态，下次点击「远程控制」即可重新配对。会议中的屏幕共享可独立使用。
共享帧率来自实际帧计数；实际收发码率与输入确认往返时间可用于诊断。WebRTC 自身 RTT 在本次环境未返回可靠值。
语音转写与会议纪要暂缓；当前会议最多四人，协作远控仍限两人。

## 应用场景与使用边界

以下说明基于截至 2026-11-04 的代码与验证记录。当前定位是可信网络内、可设置本地确认的双人桌面协作及最多四人的会议开发验证。Windows 与 Linux 已有跨机功能验证，但尚未完成所有电脑、网络和长时间运行的产品化验收。

| 场景 | 当前可用能力与边界 |
| --- | --- |
| 公司 / 实验室内远程协助 | Windows 与 Ubuntu X11 可互相请求控制，适合查看桌面、协助操作普通应用、排查开发环境；被控方须在本机允许，Windows 被控的实际点击手感仍待验收。 |
| 代码、文档与软件演示 | 共享整个主屏幕，VP9 4:4:4 优先保留文字和彩色细线；同一时间只能一人共享，不支持单窗口选择或多屏切换。 |
| 双机交换工作文件 | 远控授权期间双向复制文件 / 文件夹，再在目标电脑粘贴；适合临时交换资料，不提供文本剪贴板同步或持续目录同步。 |
| 二至四人视频交流与讲解 | 会议房间自动连接摄像头和语音，成员入退会独立处理；一人向其余成员共享屏幕，共享者批准后可切换一位成员控制共享桌面。两台电脑真实摄像头链路及四进程回归已通过，Ubuntu 图像偏暗、真实音频与长时间通话待验收，建议使用耳机。 |
| 公司与家庭之间的试用 | 可在已有路由或 VPN / Tailscale 互通的前提下尝试；跨网性能与连接可靠性尚未验收，不宜作为日常远程办公的可靠性承诺。 |

不适用于无人值守运维、超过四人的会议、游戏等对持续低延迟要求高的场景，也尚不能替代成熟的公网远控或会议服务。

## 适配电脑与运行条件

| 项目 | 当前基线与要求 |
| --- | --- |
| Windows 客户端 | Windows 11 x64，需有可用的交互桌面；桌面采集使用 D3D11，画面显示依赖 Qt / OpenGL 与正常的显卡驱动。普通权限程序不能控制更高权限的应用，UAC 安全桌面不支持。 |
| Linux 客户端 | Ubuntu 22.04 x64，当前桌面采集、被控输入和文件剪贴板依赖 X11，实机验证使用 GNOME X11；Wayland 暂不支持。 |
| 其他平台 | Windows 10、其他 Linux 发行版尚未验收；没有 macOS、手机、浏览器或 ARM 客户端交付。 |
| CPU 与显卡 | 需要为实时编解码留出 CPU 余量；通用路径为 VP9 4:4:4 软件编解码，Linux 可选 VA-API 编码须探测成功，否则回退软件。独立显卡不是已确立的必要条件，也不能保证高帧率。 |
| 内存与磁盘 | 尚未测定统一的最低内存 / CPU 配置。文件接收会占用本地临时磁盘，粘贴生成副本还需目标盘空间；按待传文件总量预留空间。 |
| 显示器 | 窗口最小尺寸为 1040×720 逻辑像素，高 DPI 缩放会影响可用布局空间；主要性能记录基于 1920×1080 主屏幕，其他分辨率 / DPI / 刷新率组合仍需实测。 |
| 会议设备 | 每位成员均需可用的摄像头、麦克风、音频输出及相应系统权限；当前不支持纯语音入会，缺少设备会使通话失败。没有声学回声消除，建议使用耳机。 |
| 运行依赖 | 远控、共享和会议均需启用 GStreamer，并带齐 Qt、媒体插件和运行库。使用完整部署目录运行；自行从源码构建才需要下文的 MSVC / GCC、CMake 等开发工具。 |

已有验证记录中的电脑为 Windows 11 / i7-11800H（8 核 16 线程）/ RTX 3060 Laptop，以及 Ubuntu 22.04.5 / i7-1355U（12 逻辑线程）/ GNOME X11，均使用 1080p 主屏幕。这是测试样本，不是最低配置，也不表示相同型号必定稳定 60 fps。低功耗电脑、虚拟机及其他硬件组合应先试运行，观察实际编码、接收、绘制帧率和资源占用。硬件原始记录见 [验证记录](docs/validation.md)。

## 网络要求

屏幕共享在已验证源地址属于 Tailscale `100.64.0.0/10`，或对端位于所选网卡子网之外时，自动使用 WAN 策略，最高 1920×1080 / 30 fps、VP9 4:2:0。GCC 从 4 Mbps 启动，在 128 kbps～12 Mbps 预算内调整，编码目标保留 20% 余量。编码端跟不上时连续两个 1 秒窗口即降档；只有对端掉帧而编码正常时要求连续四个窗口，避免一次链路停顿把整场会话压到低档，稳定后逐步恢复。WAN RTP 封包为 1100 字节，为 VPN 路径的协议开销留出余量。WAN 接收缓冲默认 400 ms，按时钟交付帧，优先流畅度，相比 200 ms 配置增加约 200 ms 画面延迟。`ZJDESK_WEBRTC_LATENCY_MS` 可选择 30、50、100、150、200 或 400 ms。实际帧率取决于双端性能与链路容量。两端需运行新版并验证对端可达地址，再由被控端授权。实现、实测和验收边界见 [跨网 1080p30 验证](docs/validation-wan-1080p30-20261110.md)。

入房使用的信令连接与传输画面 / 音频 / 文件的 WebRTC 连接是两条路径：**校验码配对或会议入会成功，不代表媒体和远控通道已连通。**

| 项目 | 要求与建议 |
| --- | --- |
| 信令服务 | 双方连接同一个可达的新版服务；远控输入对方 9 位校验码，会议输入相同会议房间码。默认监听 `127.0.0.1:8765`，仅本机可访问；跨机须绑定可达网卡或 `0.0.0.0`，并允许服务端 TCP 8765（更改端口后以实际值为准）。 |
| 媒体与数据通道 | 服务只转发协商消息，不中转媒体或文件。两端的 ICE 候选地址须可互通，防火墙需允许客户端使用协商的 TCP / UDP 连接；只开放服务端 8765 不足以保证画面和控制可用。当前没有固定媒体端口范围的配置入口。 |
| 局域网 | 优先使用双方有线千兆连接、低丢包和低抖动的局域网；千兆是推荐测试条件，不是测定的最低带宽。不同子网之间仍须具备路由和防火墙放行条件。Wi-Fi 拥塞、客户端隔离或访客网络可能影响连接和流畅性。 |
| 跨网 / VPN | 当前没有配置 STUN / TURN，也没有独立公网 NAT 穿透方案。已有 VPN / Tailscale 须同时满足信令与两端媒体地址可达；只部署公网信令服务无法解决双方 NAT。Tailscale 的 direct / DERP 与媒体显示的 TCP / UDP 是不同概念，中继可能显著增加延迟、降低吞吐。 |
| 带宽 | 以发送端实际可用上行和接收端下行的较小值为准，并为音视频并行、文件复制及关键帧突发留余量。屏幕软件编码默认按档位选择约 2～40 Mbps 的目标，拥塞控制可进一步降低预算，实际码率也可超过预算；会议 720p30 的视频目标约 2 Mbps、单声道 Opus 约 32 kbps，均为每个发送方向的编码参考值，不是线路最低配置或限速保证。四人采用全互联，每台发送三路，720p30 档位的上行目标合计约 6 Mbps 视频加音频与协议开销；CPU 同时承担三路编码和解码。 |
| 延迟与稳定性 | 尚无经过验收的通用最大 RTT / 丢包阈值。已接线局域网的一轮负载测试 RTT 为 0～1 ms、无丢包；跨网即使短测 RTT 为 3～4 ms、TCP 吞吐约 24.75 Mbps，也未通过稳定画面验收。不能仅凭宽带标称速率或 ping 判断远控是否流畅。 |
| 访问范围 | 当前没有账号认证和房间密码，内置信令使用 `ws://`，没有启用 TLS；WebRTC 媒体 / 数据通道的加密不能替代信令认证。应限制在可信局域网或受控 VPN 内使用，不直接暴露为公开互联网服务。 |

本地局域网部署运行不依赖外网或云端中继；两端仍需使用兼容版本的客户端与信令服务。网卡 / DHCP 地址变化后，应更新或移除 `ZJDESK_WEBRTC_LOCAL_ADDRESS`，在运行诊断中核对实际媒体地址。具体启动方式见下文“局域网”和“不同局域网，通过 Tailscale 连接”。

带宽与公网实测条件见 [公网优化记录](docs/wan-optimization-20261025.md)，有线局域网性能见 [1080p60 实施进度](docs/1080p60-implementation-progress.md)；这些历史数据不代表当前所在网络的实测状态。

## 当前局限与验收状态

- **人数与功能隔离**：会议房间最多四人、协作房间最多两人，一个客户端同时只能加入一个房间；协作空间用于双人远控，会议房间用于音视频、共享屏幕、多人标注及共享者批准后的单人桌面控制；共享者可在参会者间切换控制权。
- **画质与性能**：优先保留原分辨率和 4:4:4 色彩，当前为轻微有损编码。自动帧率最高 240 fps 是参数上限，不是性能保证。2026-10-30 有线局域网在可选 GCC / ICE-TCP 配置下，60 秒压力测试平均显示约 59.94 fps；持续稳定 1080p60、其他硬件及跨网条件尚未验收。
- **操作延迟**：视频接收缓冲默认 200 ms，本地光标即时移动不等于远端窗口即时响应。Linux 控制 Windows 时，用户反馈的放大画面点击迟缓 / 漏响应仍未定位；独立测试窗口收到点击不能替代实际操作验收，见 [Windows 被控验证](docs/validation-windows-host-20261103.md)。
- **桌面与权限**：只共享主屏幕，不支持窗口选择、多显示器切换、Wayland 被控或 UAC 安全桌面；远控须本地确认，没有无人值守接入流程。
- **文件与剪贴板**：只在远控授权期间同步文件，一批最多 4096 个文件 / 目录，拒绝符号链接和 Windows 不兼容名称；不支持文本剪贴板、文件拖放或中文输入法同步。断开会取消未完成批次，已接收文件须在退出客户端前粘贴；公网及大文件长时间传输仍待验收，见 [文件剪贴板验证](docs/validation-file-clipboard.md)。
- **音视频**：不包含桌面系统声音、纯语音入会、回声消除或会议网络拥塞自适应；隐藏摄像头 / 静音仍保持采集，离会才释放设备。真实摄像头双机链路及两机四进程测试通过，Ubuntu 图像偏暗尚未确认内容，真实音频、四台实体机和持续通话尚未完整验收，见 [视频会议](docs/video-conference.md)。
- **恢复与交付**：断线后需手动重新入会，尚无自动重连；语音转写和会议纪要暂缓。当前提供本地部署目录，没有正式安装包，干净电脑安装、完整双平台云端 CI 和长期稳定性验收尚未完成。

## Windows 快速开始

在 VS Code 中打开本项目，选择“终端 → 新建终端”，使用 **PowerShell** 执行：

```powershell
cd F:\projects\ZJdesk
.\build.ps1
.\run.ps1
```

默认构建 Debug。构建脚本自动找到 VS 2022，加载 MSVC x64、CMake、Ninja 和 Qt 环境，
依次完成配置、编译和无界面的测试；启用媒体后增加 media 回归，任一步失败即停止。无需使用 Developer Command Prompt。
默认不运行会弹出窗口的 `desktop` 界面测试；需要完整测试时执行 `.\build.ps1 -GuiTests`。
项目只提供两个 PowerShell 入口：`build.ps1` 负责构建，`run.ps1` 负责启动。
修改代码后重新执行构建脚本即可增量构建；构建前关闭上一次演示窗口，避免可执行文件被占用。

启动脚本打开一个客户端窗口；未指定 `-ServerUrl` 时同时启动后台信令服务。
连接另一台电脑时传入 `-ServerUrl 'ws://服务机器IP:8765'`，远控页面自动获取本机校验码，输入对方码连接；会议仍输入相同房间码加入。会议房间码为 1–32 位字母、数字、下划线或连字符，区分大小写；必须连接同一个信令服务。会议房间需要支持房间类型的新服务端；若服务端过旧，客户端会提示更新。
终端会保持运行；关闭客户端后脚本停止自己创建的服务。
在该终端按 `Ctrl+C` 会清理本次脚本创建的客户端和服务，不影响其他实例。
不会修改全局 PATH、系统配置或现有 Qt 5 项目。

Qt 安装位置不同时，两个脚本都可传入 `-QtRoot '实际的 Qt MSVC2022 x64 目录'`。

构建和运行 Release：

```powershell
.\build.ps1 -Preset windows-release
.\run.ps1 -Preset windows-release
```

构建输出位于 `build/windows-debug/bin/` 或 `build/windows-release/bin/`。
如果 PowerShell 提示脚本执行被策略禁止，可以用下列命令仅为本次进程运行脚本：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run.ps1
```

### 局域网

显式使用其他服务时，两端启动参数传入相同 `--server ws://服务机器局域网IP:8765`；服务机器须是这两台电脑之一。远控使用对方校验码，会议仍加入相同会议房间。

已验证这两个子网可以互通，SSH 使用 `orbbec@10.11.47.137`。
仅修改信令地址不会限制媒体网卡。需要明确验证纯局域网时，在各自启动进程前设置
`ZJDESK_WEBRTC_LOCAL_ADDRESS` 为本机局域网地址；候选收集只使用该地址，
ShareStats 的 `localAddress` / `remoteAddress` 记录实际选中地址。未设置时保留自动收集，
地址变化后须更新或移除此进程环境变量，不修改系统路由或 Tailscale 配置。
首版没有账号和房间密码，定位于局域网开发验证；公网部署属于后续版本。

### 不同局域网，通过 Tailscale 连接

两端已加入同一 Tailnet 时，Linux 新版客户端自动提供共用信令服务。
Windows 填 Linux `100.87.60.58`，Linux 填 Windows `100.122.3.99`，两端分别点击「连接服务」，再按被控端的二次验证设置授权。
启动验证会选择本机 Tailscale 源地址并更新 `ZJDESK_WEBRTC_LOCAL_ADDRESS` 与 `ZJDESK_WEBRTC_PEER_ADDRESS`，自动启用 WAN 1080p30 策略。
其他路由可用 `ZJDESK_SHARE_WAN=1` 显式启用；受限链路可用 `ZJDESK_SHARE_LOW_BANDWIDTH=1` 优先选择原 540p15 / 800 kbps 策略。`ZJDESK_WEBRTC_MAX_BITRATE` 可覆盖 GCC 上限（128000～40000000 bit/s），编码仍受当前画质档位约束。
显式指定服务时，Windows 启动可传入 `-ServerUrl 'ws://100.87.60.58:8765'`。
媒体 ICE host 候选不限制局域网网段，能够使用 Tailscale 虚拟网卡地址，无需把 IP 写入代码。
本次将媒体启动等待改为 45 秒、控制请求及允许后的连接等待改为 60 秒；
Linux 等待本地批准仍为 30 秒，拒绝、撤销和断开仍立即清理。
Tailscale 的 direct / relay 路径独立于界面显示的媒体 TCP / UDP；DERP 中继可能增加延迟并限制实际速度。
2026-11-08 在当前 direct 路径完成双向桌面帧、原生移动与点击验证，详情见 [跨网验证](docs/validation-crossnet-20261108.md)。
此前 DERP 中继链路验收未通过，记录见 [历史验证](docs/validation.md)；本轮没有复测中继，也未实现脱离 Tailscale 的公网 NAT 穿透或 TURN。

### 启动快捷方式与双端开发启动器

双击 `构建启动.bat` 使用 `orbbec@10.11.42.4` 通过 SSH 构建启动双端，跳过测试；构建期间请勿修改源码。它使用 `-ForceRestart` 强制结束两端已有 ZJdesk 进程。双击 `直接启动.bat` 则跳过构建、测试和部署，直接打开本机已部署的客户端。两端均需在协作空间验证对端 IP。需要回归验证时请分别运行两端构建测试。

开发者也可显式执行 `start-both.ps1` 并指定其他 SSH 地址；以下缓存、选网卡和重启行为属于这个开发入口。

Windows 继续复用 `build/windows-release`；Linux 按 Windows 机器和工作树路径复用 `build/start-both-cache.<hash>` 独立目录。同步包括未提交源码，按内容校验，仅更新变更文件并清理已删除的源码，保留编译缓存和部署目录，Linux 原项目源码保持原样。首次使用新缓存需要完整编译，后续仅编译变化及其依赖；Linux 需要 `rsync`。已有的旧快照目录保留。
`start-both.ps1` 启动时通过 SSH 查询 Linux 当前地址，优先选择可达的有线接口，没有可达有线地址时回退 Wi-Fi；Windows 同样优先选择当前可用的物理有线接口，不能到达所选 Linux 地址时回退 Wi-Fi。逐对检查源地址、网卡路由及绑定源地址的 TCP 连通性，随后信令和两端媒体使用同一组地址，不再固定旧 IP。Docker / VPN 等虚拟接口不参与自动选择，仍可手动指定。两端的选择不依赖谁是控制方；只在启动时选择，切换网络后需要重新启动连接。

未传 SSH 地址时，启动器先提示查询方法并要求输入 `用户名@Linux当前IPv4地址`，也可传入 `-LinuxSsh '用户名@当前可达地址'`，不再内置固定候选。需预先配置免密登录、核对主机密钥，并按实际机器指定 `-LinuxRoot` 和 Linux 桌面环境。有一个候选可登录时，会查询到其他网卡的新地址。需要固定网卡时传入 `-LinuxAddress 'Linux当前IPv4地址'` / `-WindowsAddress 'Windows当前IPv4地址'`；显式地址失效时报错。两端客户端随后仍需完成 [启动网络验证](docs/startup-network.md)。原选网卡验证见 [有线 / 无线启动验证](docs/validation-network-startup-20261105.md)。

`start-both.ps1 -ForceRestart` 先强制结束 Windows 上的 `zjdesk.exe` / `zjdesk-server.exe`，以及 Linux SSH 用户名下的 `zjdesk` / `zjdesk-server` 旧实例，再检查 8765 端口并继续构建启动。无法结束进程或端口仍被其他程序占用时停止并报错。

### Windows 与 Linux 双向远程控制

Linux 桌面运行 `bash ./run.sh`，Windows 运行：

```powershell
Remove-Item Env:ZJDESK_WEBRTC_LOCAL_ADDRESS -ErrorAction SilentlyContinue
.\run.ps1 -Preset windows-release -ServerUrl 'ws://Linux当前可达IP:8765' -Name Windows
```

手动启动 Linux 可用 `bash ./run.sh`，在协作空间填写并验证 Windows IP；成功后会用自动识别的本机地址覆盖旧的媒体绑定。两端默认共用 Linux 信令服务。有线优先的自动探测由上面的双端启动器完成。
不同网络经 Tailscale 的验证已于 2026-11-08 恢复，当前 direct 路径结果见 [跨网验证](docs/validation-crossnet-20261108.md)，历史局域网结果见 [validation.md](docs/validation.md)。

两端均更新客户端和信令服务后启动，在协作空间互相填写对端 IP 并点击「连接服务」。
设置 → 远程控制中的“需要二次验证”默认开启：被控方点击“允许控制”后连接；关闭后，匹配的对端可自动获得远控和文件复制权限。IP 地址不提供身份认证。Windows 和 Linux 两个方向使用相同流程。
对方离线、未验证本机地址、正在连接其他电脑或同一地址存在多个匹配客户端时会提示，可检查后重试。
控制方点击收到的画面后操作键鼠；“放大画面”进入全屏，按 Esc 返回，任一端点击“结束控制”都会断开双方配对，下次可点击连接重新发起。
Linux 被控要求 X11；Windows 被控支持普通交互桌面，SendInput 受 Windows 权限边界限制，不能控制 UAC 安全桌面或比本程序权限更高的应用。
Wayland 被控、文本剪贴板和中文输入法同步尚未实现。两端需要启用 GStreamer；普通局域网保留 VP9 4:4:4 路径，跨网低带宽模式使用 VP9 4:2:0 以降低传输需求。
自动模式结合双端处理速度和网络反馈逐步升降档；目标帧率不是实际帧率，也不保证任意两台电脑都能稳定 1080p60。

### Windows 与 Linux 双向复制文件

两端都需要更新到支持双向文件剪贴板的版本。远控授权同时包含双方文件复制（关闭二次验证时也会自动授权）；普通屏幕共享和视频会议不会同步文件。

1. 建立远控后，在来源电脑的文件管理器选中文件或文件夹，按 Ctrl+C。
2. 等待远控状态提示“已就绪”；文件先通过 WebRTC 传到目标电脑临时缓存。
3. 切换到目标电脑的文件管理器，按 Ctrl+V。Windows → Linux 时，可在 Windows 复制后点击远控中的 Linux 目标文件夹，再按 Ctrl+V；反向则在远控画面内复制 Linux 文件，再切到 Windows 文件夹粘贴。

支持多选、子目录、空目录和中文文件名；一次最多 4096 个文件 / 目录，名称须兼容 Windows，不支持符号链接。
源文件变化、断开连接、收回控制或传输期间在接收电脑重新复制内容会取消未完成的传输，可重新 Ctrl+C 重试。
文件复制不会删除源文件（剪切也按复制处理）。已完成的缓存保留到接收端客户端退出，停止控制后仍可粘贴；请在退出客户端前完成粘贴。
支持 Linux X11；不同步文本，不支持 Wayland。收到的文件不会自动传回。旧版对端只协商已有的单向能力。实机验证和限制见 [验证记录](docs/validation-file-clipboard.md)。

## 启用 GStreamer、摄像头与屏幕共享

默认 `ZJDESK_ENABLE_GSTREAMER=OFF`，因此安装媒体 SDK 前也可以维护和测试房间逻辑。
准备同版本 MSVC x64 Runtime 与 Development 的共同目录后，首次在 PowerShell 中执行：

```powershell
.\build.ps1 -GstRoot '实际的 GStreamer SDK 目录'
.\run.ps1
```

之后两个脚本从对应 preset 的 CMakeCache 读取 SDK 路径；只设置子进程的 DLL、插件、
扫描器与独立注册缓存，不修改系统 PATH。`build.ps1 -WithoutMedia` 可显式关闭媒体。
Qt Creator 使用 `ZJDESK_ENABLE_GSTREAMER=ON`、`GST_ROOT=<真实 SDK 目录>`，并配置对应运行环境。

本机 SDK 是校验官方 MSI 后提取的独立目录：
`F:\gstreamer\1.26.11\PFiles64\gstreamer\1.0\msvc_x86_64`，没有写系统安装记录。
本机首次启用可将该路径传给 `-GstRoot`；它不是其他机器的默认路径。

Windows 启动时只读检查“摄像头访问”和“允许桌面应用访问摄像头”开关；明确关闭时弹出授权引导，点击“打开 Windows 摄像头设置”，
程序请求 Windows 直接打开“摄像头”隐私页面，在该页面允许摄像头和桌面应用访问。
开关已开启时刷新设备不会重复弹窗；无法读取或识别开关时显示“无法预先确认”，仍可尝试视频会议，实际访问由采集后端和 Windows 检查。
如果系统设置无法启动，会弹窗显示失败原因及备用打开方法，可以再次尝试。
返回程序会重新检查权限并刷新设备；“暂不使用”不会授予权限，之后可点击“刷新设备”再次授权。
此桌面程序通过 Windows 设置完成授权，程序内的按钮不能代替系统授权，也不会自动开启摄像头。

本机 2026-11-02 实测发现项目路径存在摄像头访问差异；完整副本 `C:\Users\29822\AppData\Local\Programs\ZJdesk\zjdesk.exe` 所在目录已通过真实摄像头三次采集 / 释放测试。项目内启动入口仍使用原路径，具体限制来源与主窗口预览确认进度见 [验证记录](docs/validation.md)。

在侧栏“设置”中选择会议摄像头、麦克风和扬声器。独立本地预览已移除，通话时显示本机与远端画面；界面不提供视频测试源。
每次进入“视频会议”页会重新枚举一次摄像头；没有摄像头时，摄像头选择框显示灰色的“无可用设备”。
视频会议按“最高分辨率优先，再取对应最高帧率”启动；不再把真实摄像头固定为 640×480 / 30 fps。
运行中按实际采集、帧交接与会议编码速度调整输出：先保留分辨率降低帧率，持续吃紧才降低尺寸，稳定后自动恢复。
摄像头输入保持设备公布的最高原生模式；自动调整作用于后续输出，不会造帧。
支持设备公布的 raw / JPEG 模式；不能以软件设置超过摄像头硬件能力，驱动或权限错误会显示失败原因。
在“设置”中点击“测试声音”播放低音量测试音，再次点击停止。
诊断页显示真实版本、枚举设备和音频测试状态；默认测试不打开摄像头，也不播放测试音。

远控双方通过校验码连接，或两人会议加入同一会议房间后，点击“共享主屏幕”，另一端自动显示整个主屏幕及鼠标指针。
Linux 桌面发送默认使用 WebRTC ICE-TCP，避免高画质大关键帧在当前无 UDP 发包调度时突发丢失；
画面状态显示实际 TCP / UDP。TCP 拥塞时可能增加等待，不能据此承诺稳定 60 fps。
共享从主屏幕原始像素尺寸及刷新率开始，在原尺寸下逐级选择可持续帧率，
降至 24 fps 仍持续不足时才按比例缩小，仅最低尺寸继续降帧；不会放大原本较小的屏幕。
VP9 保留 4:4:4 色彩，默认允许轻微有损以减少大帧和带宽压力；软件量化范围为 0～8，线程数为 1～8。
Linux 可选探测 VA-API VP9 profile 1 编码，启动及自动模式尺寸切换通过后才使用；失败回退软件编码。
硬编使用 CQP 8～16，实际码率不受目标预算硬性限制；Windows 接收仍使用软件解码以保留 4:4:4。
连续丢包或相对基线的持续往返延迟会保守降低编码预算，拥塞期间不自动升档；稳定后逐步恢复。
另有 Linux 发送端 `ZJDESK_WEBRTC_GCC=tcp` 可选路径，使用实际协商的 TWCC 和单层 GCC pacing 并保留 ICE-TCP，
需要可选 rsrtp / rtpgccbwe 插件；普通局域网下不设置或设为 0 保留原 ICE-TCP、不开启 GCC。
WAN 和显式低带宽模式自动启用 GCC 并保留 UDP 候选；显式设置 `ZJDESK_WEBRTC_GCC=tcp` 仍会保留 Linux 的 ICE-TCP 限制。
2026-10-10 的 LAN 十分钟真实 Edge 隔离桌面对照平均显示 52.73 fps、保持 1080p，
仍有最长约 907 ms 停顿，尚未达到稳定 60 fps；完整结果和物理 GNOME 验证边界见 docs/validation.md。
设为 1 的 UDP 候选在物理 GNOME 首帧复验失败，不用于当前日常客户端。公司 LAN 对照结果见 docs/validation.md，
不能推广为跨网保证。两端鼠标位置在进入媒体线程前合并，离散按键和授权事件仍保持顺序；不含系统声音。
传输保留 NACK / RTX，增加 RED / ULPFEC；仅为本会话的直连 UDP socket 申请缓冲，不修改系统网络参数。
两端为 RTCP 反馈明确保留 64 kbps 预算，避免启动期自动预算过低导致重传反馈晚于接收期限。
全屏移除边距与底部控件，占满屏幕；远端与本机屏幕像素尺寸相同时按 1:1 显示。
退出按钮悬浮于右上角，Esc 仍可返回；普通窗口按尺寸适配时使用平滑缩放。
调整时保持 WebRTC 连接和当前共享；连续稳定后才试探恢复上一档，避免频繁升降。
接收窗口在后台或最小化时，不把暂停重绘计为性能不足；回到前台重新采样显示帧率。
原尺寸优先是为了保留桌面文字清晰度，并非保证每台电脑都能达到原尺寸 60 fps。
双方必须使用更新后的客户端和信令服务；本机 30 / 60 fps 对比及限制见 docs/validation.md。
同一时刻一人共享；停止后可由任一成员重新共享。会议中一位观看者离开不影响其他观看者；共享者离开、最后一位观看者离开或信令中断时停止并清空共享画面与标注。
共享会发送整个主屏幕，可点击“停止共享”结束。当前不提供窗口选择、多屏切换或公网 TURN。
Windows 使用 D3D11 桌面采集；Linux X11 使用 ximagesrc，Wayland 暂不支持。

.\build.ps1 -Preset windows-release -GstRoot '实际的 GStreamer SDK 目录' -Deploy
