# WAN 延迟测量与首轮对照记录

2026-11-11，工作目录为 `C:\Users\29822\.codex\worktrees\zjdesk-2-bound\ZJdesk`，分支 `codex/ZJdesk-2`，代码基线 `bebb3c129b929eb6d9f4144a50f64b3fdf936493` 加本轮未提交修改。依据原始检出的 [实施计划](F:/projects/ZJdesk/docs/wan-1080p30-low-latency-plan-20261111.md) 完成 P0 测量入口并开展 M0 / P1 首轮采样。默认 WAN 接收缓冲为 400 ms。

新增 `zjdesk-latency-probe`，测量接收端发出 DataChannel 标记请求，到发送端将代次及序号写入下一张合成帧，再经 VP9 / I420 编解码到接收端 `VideoSurface::frameSwapped` 的测试闭环。起止时间均使用接收端单调时钟，包含控制消息往返和帧调度。该值用于同条件对照，实际系统输入、真实桌面采集与物理屏幕显示延迟另行验收。

接收诊断记录请求缓冲、`webrtcbin` 读回值、各子 `rtpjitterbuffer` 读回值、appsink sync、segment 映射 PTS 与本地运行时钟差，以及原有分段耗时。PTS 时钟差属于本地播放调度诊断。原始日志逐帧记录实际新帧 swap、逐请求记录序号、超时与发送端标记应用事件。

离线分析保留完整一秒窗口中的零帧秒，按原始样本计算 nearest-rank 分位数，计入观测窗口首尾空档。旧代次、重复及无法关联的回执会使关联验收失败。短测至少 200 个有效标记，30 分钟及以上至少 1000 个。自动统计门槛仍需结合独立路径记录核对配对条件。

Windows 包装器使用独立原生 Desktop，透传原生退出码，超时终止并等待进程退出后返回 124。两个手工探针支持 10～7200 秒。Linux 图形验证在本轮隔离目录的 Xvfb `:91` 上运行，所有测试界面均在后台。

双端 Qt 6.8.3、GStreamer 1.26.11。Windows 为 i7-11800H / Intel UHD Graphics，MSVC 2022 x64，接收呈现使用原生 Windows OpenGL 4.6，驱动报告 31.0.101.4502。Ubuntu 为 i7-1355U / GCC 11.4，独立 GLX 会话使用 Mesa 23.2.1、llvmpipe LLVM 15 软件渲染。Linux 的 frameSwapped 属于后台软件 OpenGL 呈现证据，物理扫描输出与硬件图形性能待验收。

测试固定合成 1920×1080 / 30 源，WAN=1、LOW_BANDWIDTH=0、WEBRTC_GCC=1、MAX_BITRATE=12000000。该上限为当前默认预算，实际码率随内容和 GCC 变化。短测接收端运行 260 秒，固定预热 20 秒，剩余 240 秒计入画面统计。发送端设 300 秒，接收端离开时提前正常结束。

新路径的 Tailscale ping 持续报告 direct 到 Linux 私网端点 `10.11.47.137:41641`，WebRTC 使用 UDP / Tailscale 地址。双端 netcheck 均报告 UDP 可达、映射随目标变化、同一公网出口。Windows 同时存在 Sangfor VPN 接口。上述证据覆盖当前跨子网直连路径，独立公网 NAT / DERP 场景待验收。

新网络正向单组对照中，200 ms 的 p50 改善 179.74 ms，p95 反而增加 10.64 ms，没有达到 p95 至少改善 80 ms 的门槛，整体未通过。当前默认档位为 400 ms。该结论来自单组正向样本，后续还需稳定路径下每方向三组配对，达到门槛后再进入长测及 150 ms 候选。

反向 400 ms 基线的 240 个完整秒中有 2 个零帧秒，标记覆盖率为 98.72%，缓冲与子 jitterbuffer 均读回 400 ms，双端正常返回 0。该轮接收端为 llvmpipe 软件渲染，后续双向性能比较需同时考虑呈现后端差异。400 ms 两方向基线均存在秒级空档，降低缓冲的正式配对及推广条件尚未满足。

开发校准中的首次双机探针因遗漏 GStreamer 初始化而崩溃，补上 `MediaEnvironment::inspect()` 后重建。随后 `smoke-fwd-v2` 成功收发并记录 Windows 实际 OpenGL renderer，9 个预热后样本 p50 444.44 ms、p95 480.64 ms，样本量不足正式门槛。校准还发现初始化时间混入探针时长，已把媒体初始化及初始窗口创建移至正式计时前。旧网络 400 ms 的发送端曾在接收端正常退出后返回 4，已修复为收到 peer_left 后正常结束，新网络两轮双端均返回 0。

首轮自然停顿时发送端编码输出最大间隔约 67 ms，Windows 接收 worker 最大耗时约 109 ms，接收端出现丢包及解码输出空档。RTP 接收计数在停顿期间仍增长，需要继续区分传输波动、修复等待和 VP9 参考帧恢复。

该合成源的正向解码 p95 在 400 / 200 ms 两轮分别为 3.0 / 1.9 ms，接收帧到 swap 的最大耗时分别为 26.56 / 10.11 ms。解码输出最大间隔为 1157.21 / 833.11 ms，sink 到 pull 最大间隔为 702.90 / 578.44 ms，本地播放时钟差最大正值为 605.65 / 301.96 ms。这些数据支持先细分接收修复和播放等待，真实动态桌面的编解码成本还需独立测量。
