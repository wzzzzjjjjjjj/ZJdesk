# ToDesk、向日葵、UU远程与 ZJdesk 技术策略对比分析

调研日期：2026-11-17。ZJdesk 源码基线：`ZJ-desk` 分支，`5bcd349`，项目版本 `0.4.5`。

本报告回答：这些软件的远程控制原理是否与 ZJdesk 相同，为什么体验可能不同，以及 ZJdesk 应优先验证和改进什么。范围是桌面远控；摄像头视频会议不作为本次编解码对比对象。

## 1. 结论：总体链路相似，具体实现与控制策略不能视为相同

四者都需要完成一类共同任务：建立连接与授权、传回桌面、传递键鼠操作、执行输入，再把操作结果显示回来。ZJdesk 走的技术方向合理，并不是采用了一条与商业远控完全不同的路线。

但“都能传画面、传键鼠”不代表底层框架、传输协议、编码器、缓冲策略和公网连接能力相同。公开证据支持以下判断：

| 产品 | 能确认的重点 | 与 ZJdesk 的关系 |
| --- | --- | --- |
| ToDesk | 官方披露 RTC/RTP、拥塞控制、动态抖动缓冲、重传与前向纠错，以及 SD-WAN 选路；当前产品页还介绍鼠标加速通道与 GPU 解码 | 实时传输原理有相似处，但没有证据证明采用相同的 GStreamer/WebRTC 栈、VP9 配置或参数 |
| 向日葵 | 官方介绍 HSKRC、P2P 优先与服务器中转；不同模式分别偏重办公、画质或流畅，其中办公模式说明调用微软 RDP | 不能把所有模式当作 ZJdesk 式视频管线；共享桌面与 RDP 路径必须分开比较 |
| UU远程 | 官方确认专网节点、自动画质、自定义码率、游戏鼠标/键位支持；帮助文档涉及 H.264/H.265 和 4:4:4 条件 | 具备相似功能目标，但没有可靠公开证据确认其内部采用 WebRTC、RTP、QUIC 或何种修复算法 |
| ZJdesk | 当前源码明确为 Qt/C++、GStreamer `webrtcbin`、VP9 屏幕流、DataChannel 输入、平台输入注入，以及 LAN/Tailscale 路径选择 | 源码可核查；已有抗丢包和低延迟措施，但其效果仍须按真实链路验证 |

**不能据此给出“谁快几倍”的排名。** 本次没有安装三家软件进行同机横测，也没有抓包、逆向或检查商业客户端实现。厂商公布的最高帧率和最低延迟，不是本报告的测量结果。

## 2. 证据范围与阅读方法

报告采用三种证据标记：

- **源码确认**：当前 ZJdesk 或对应依赖版本的实现可直接核对。
- **官方披露**：厂商技术文章、帮助中心或产品页的说明；仅代表该资料覆盖的版本、模式和条件。
- **分析判断 / 未披露**：根据机制提出的推论或尚无可靠资料的部分，不能当成商业软件的已知实现。

资料限于 `todesk.com`、`service.oray.com` 和 `uuyc.163.com` 等官方来源。名称相近的下载站、转载和“评测”不作为内部技术证据。2022—2023 年的技术文章用于理解公开路线，不用于断言 2026 年所有版本的每次会话都采用完全相同的实现。

## 3. 先把共同原理与技术层次分清

### 3.1 共享桌面的基本闭环

典型闭环可以写成：

```text
控制端键鼠 → 输入消息 → 网络 → 被控端校验与注入 → 应用响应
                                                    ↓
控制端显示 ← 解码/播放调度 ← 网络 ← 压缩编码 ← 桌面采集
```

大部分共享桌面远控都面临这个闭环，但不保证都使用相同 API，也不保证每种模式都把整张桌面作为视频传输。RDP 是另一类远程桌面协议路径，不能直接等同于一条固定的屏幕视频管线。

鼠标图标可以在控制端本地立即移动；被拖动的远端窗口仍要经过完整闭环。商业软件中的鼠标优化，也不能自动证明窗口内容获得同样低的反馈延迟。

### 3.2 容易混淆的词并不处于同一层

| 层次 | 例子 | 要回答的问题 |
| --- | --- | --- |
| 桌面能力 | 共享控制台桌面、RDP 模式 | 操作的是哪种桌面，会话语义是什么？ |
| 连接与选路 | P2P、中转、SD-WAN、Tailscale | 两台设备怎样连通，数据走哪条路？ |
| 实时通信框架 | RTC、WebRTC、GStreamer `webrtcbin` | 怎样组织协商、媒体、反馈和数据通道？ |
| 压缩编码 | VP9、H.264、H.265 | 怎样减少画面数据量？ |
| 网络与消息传输 | UDP、TCP、RTP、SCTP | 怎样承载数据、排序与重传？ |
| 动态策略 | 拥塞控制、缓冲调整、降码率、关键帧恢复 | 网络变化时优先保什么、牺牲什么？ |

因此，“ToDesk 使用 RTC”不能证明它使用 WebRTC；“支持 P2P”也不能说明使用哪种编码。UU 介绍 DTLS/AES，同样不足以反推出其采用 WebRTC。

RTP 通常运行在 UDP 等下层传输之上，不是与 UDP 互斥的替代物。TCP 也不是每发一个包都必须等确认才能发下一个包；这里不沿用部分营销文章中的简化解释。

## 4. ToDesk：公开路线更强调实时传输与网络基础设施

### 4.1 官方披露了什么

- **桌面编码**：官方技术文章介绍针对桌面内容的冗余优化、参考帧安排和 GPU 采集/编解码路线；不足以据此认定当前全部版本统一使用某个标准编码器。[T1]
- **实时传输**：公开 RTP、时延与丢包反馈、动态抖动缓冲，以及重传结合前向纠错的设计。[T2]
- **网络选路**：公开 SD-WAN 对接入和骨干线路的探测、选择与调度，并介绍 SRv6、DPDK 等基础设施技术。[T3]
- **产品策略**：当前性能页介绍独立鼠标加速通道、本地 GPU 解码等能力；FAQ 表明固定帧率、游戏模式和 RTC 路径受版本影响，精简被控端也存在限制。[T4][T5]

这里的“独立鼠标通道”是厂商公开功能描述，无法确认其内部具体是独立 socket、逻辑流还是调度队列。不能把它写成已经证实的某种 UDP 键鼠协议。

### 4.2 哪些地方与 ZJdesk 相似

都需要压缩桌面、根据网络反馈调整发送、处理丢包与抖动，并让输入和画面协调工作。ZJdesk 已有 GCC、NACK、FEC、关键帧恢复和本地光标，并非只有最基础的视频传输。

### 4.3 哪些差异有依据，哪些尚不能确定

有依据的差异是：ToDesk 公开了厂商运营的广域网线路体系及更丰富的产品策略，而 ZJdesk 当前主要依赖可达的 LAN/VPN。ZJdesk 可直接看到其缓冲和排空参数，ToDesk 的当前实际参数与控制器实现没有完整公开。

**分析判断**：动态缓冲、输入调度和更合适的链路可能改善交互，但本次不能证明 ToDesk 对当前 ZJdesk 的某一次冻结具体采用了何种解决方法。文章中的毫秒级指标也不能移作 ZJdesk 的验收门槛。

## 5. 向日葵：必须按模式比较

### 5.1 官方披露了什么

官方流畅度指南介绍 HSKRC、P2P 优先及失败后的服务器转发，并按办公、高清、游戏、极速等模式区分体验目标。其中办公模式明确说明调用微软 RDP；另有自动画质与硬件编码相关条件。[S1]

HSKRC 是厂商公开的技术名称，不能直接把它当作 H.264、VP9 这样的编码格式。官方帮助页没有完整公开当前各模式的传输栈、缓冲控制器或修复参数。

### 5.2 与 ZJdesk 的关系

对于采集桌面再传回操作的路径，仍有采集、编码、网络、解码、输入执行等共同问题；对于 RDP 办公模式，则不能直接套用 ZJdesk 的 VP9/WebRTC 管线图。

ZJdesk 当前有普通/跨网等媒体配置与画质调节，但没有实现向日葵上述完整的多模式产品体系，也没有其内置公网服务器中转服务。

### 5.3 可以借鉴的策略

重点是明确任务目标：文字办公优先清晰与按键反馈，动态画面优先连续性与可控帧龄。不同任务可以采用不同参数，但参数必须有测量依据，不能只给同一套管线换一个“游戏模式”的名称。

## 6. UU远程：公开游戏与画质能力，底层协议仍有较多未知

### 6.1 官方披露了什么

- 游戏页介绍专网节点、自动画质、自定义码率及游戏输入适配；这些说明产品提供相应能力，不证明每个会话都走某条特定专网路径。[U1]
- 真彩帮助文档涉及 4:4:4 及 H.264/H.265 的设备兼容条件，可以确认存在相关编码路径，不能推断所有会话默认使用 H.265。[U2]
- 办公页介绍 DTLS/AES 与线路调优；没有据此确认 WebRTC 或具体拥塞控制器的充分证据。[U3]

当前公开材料不足以确认 UU 的键鼠是否采用不可靠消息、具体是否使用 RTP/QUIC、FEC 比例是多少、抖动缓冲有多长，或是否预测远端窗口位置。这些项目在报告中保持未知。

### 6.2 与 ZJdesk 的关系

功能目标相似，但屏幕编码路径已有可见区别：ZJdesk 当前屏幕链路主要为 VP9；UU 官方帮助涉及 H.264/H.265。实际快慢仍取决于硬件支持、编码设置、分辨率、码率、网络和显示调度，不能仅按编码名称判断。

游戏中的沉浸式鼠标、键位和手柄适配，也比“把鼠标绝对位置和按键传过去”更广。ZJdesk 当前桌面输入不能据此宣称已经具备等价的游戏兼容能力。

## 8. ZJdesk 已有的策略，以及真正需要验证的差距

### 8.1 连接与选路：本地/VPN 可达与公网服务能力不同

ZJdesk 已有 LAN 优先、Tailscale 兜底、地址交换及线路切换恢复相关逻辑。当前没有内置 STUN/TURN 服务配置，也没有三家商业软件所宣传的厂商公网线路体系。

这里需要区分：**ZJdesk 应用内没有 TURN 中转，不代表实际会话一定直连。** Tailscale 自身可能走直连或 DERP；应读取实际路径。WebRTC 也不能一概当作 UDP，当前源码部分 Linux LAN 路径允许使用 ICE-TCP。

选路较好可能降低 RTT、抖动或拥塞，但不能抵消应用内部长期播放积压。反过来，单纯缩短缓冲也不能修复较差的链路。

### 8.2 编码与硬件：不能从“支持 GPU 采集”跳到“全程零拷贝”

当前 Windows 屏幕采集使用 D3D11，管线包含 `d3d11download`；编码以低延迟软件 VP9 为主，Linux 有可选硬件编码路径，接收端使用 `vp9dec`。这与全程在 GPU 表面上传递、硬件编码和硬件解码不是同一件事。

硬件路径可能降低 CPU 压力、改善更高分辨率/帧率的可行性，但若主要等待发生在接收播放时钟或网络修复阶段，更换编码器未必改善最主要的延迟。

4:4:4 能减少文字和彩色边缘的色度损失，不保证编码本身无损。ZJdesk 跨网当前采用 I420，不能把 LAN 的 4:4:4 条件当作跨网默认画质。

### 8.3 抗丢包：已有 NACK/FEC，不是从零补功能

`configureTransceiver()` 已设置：

```cpp
g_object_set(transceiver, "do-nack", TRUE,
             "fec-type", GST_WEBRTC_FEC_TYPE_ULP_RED,
             "fec-percentage", guint(20), nullptr);
```

这证明程序配置了重传与 FEC 意图，**不证明每次协商都成功启用，也不证明线路上永远恰好多 20% 数据**。须结合 SDP、实际插件和运行计数验证。[Z2]

下一步应比较在不同 RTT、丢包与带宽条件下，补包、冗余和关键帧恢复的时间与带宽成本。已有参考依赖的压缩帧不能随便丢弃；若需要放弃过旧数据，必须与完整性、解码参考和重新同步机制一起设计。

### 8.4 缓冲与排空：稳定性和交互时效需要一起控制

当前接收默认：

```cpp
const int defaultLatency = wideArea && !conservative ? 400 : 200;
```

直连远控解码后立即交付画面（`appsink sync=false`）。普通 WAN 的 400 ms 接收缓冲参与 RTP 排序与修复，完整输入到显示时延还包含输入、采集、编解码和呈现。[Z1]

已有 backlog 排空策略：250ms 触发、低于 120ms 退出，尝试让发送速度低于接收消费速度。当前 backlog 是相对近期最低播放偏移，不是绝对帧龄。`observeBacklog()` 还会收紧最大帧率上限；如果临时排空上限持续保留，恢复 30fps 可能受阻，这是源码风险判断，不是本次实测结论。[Z3]

最低 24fps 也意味着：当接收端实际消费能力低于该值时，不能假设降到 24fps 就能排空。需要判断瓶颈及恢复条件。

商业产品公开的“动态缓冲”说明这是一类值得优化的策略，不能据此断言其现行实现肯定比 ZJdesk 的 400ms 配置更适合所有网络。

### 8.5 输入与文件共用通道：可验证的排队风险

ZJdesk 创建 `zjdesk-control` 时未传额外选项。对照 GStreamer 1.26.11 的 `gst_webrtc_bin_create_data_channel()`，创建路径默认 `ordered=true`，重传次数和寿命均不设上限，即可靠、有序传递。[Z4][G1]

输入、光标、授权消息与文件消息共用这一通道。发送前的移动合并能减少尚未进入工作线程的旧位置，不能撤回已交给传输层的数据。文件已有每块 16KiB、请求下一块才继续的节流，不能描述为无限制灌入。[Z4][Z5]

**分析判断**：丢包重传或文件消息排队可能拖延后续控制消息，但当前没有测量证明它是用户拖动卡顿的主要原因。应先观察 `buffered-amount`、输入回执和同时传文件时的闭环变化。

若验证有影响，可以评估分离输入与文件通道、给输入更明确的调度优先级。多个 DataChannel 仍可能共享 SCTP 关联和同一网络瓶颈，分开通道不保证彻底消除竞争。

也不能把所有输入都直接改成“不可靠”：普通位置可以评估过期丢弃，按下/松开、授权/撤权则需要可靠且明确的状态语义。ZJdesk 当前还按递增序号拒绝旧事件，拆流后必须重新处理跨流顺序和拖动关系，避免按钮卡住或有效事件被误丢。

### 8.6 输入执行：可靠撤权与状态恢复同样重要

ZJdesk 使用 `epoch`、`sequence` 和本地 `generation` 校验输入，独立线程执行 Windows `SendInput` 或 Linux XTest；撤权使旧排队事件失效并释放输入。[Z6]

商业软件也需要实现输入执行，但本报告没有其内部源码，不能声称它们使用相同 API、相同序列号设计或同样的移动合并间隔。

输入回执只说明消息/注入阶段，不能证明目标应用已响应，更不能证明控制端已看到结果。所有优化最终都应回到完整输入到可见变化的闭环。

## 9. 授权与安全策略：不能把 IP 匹配当身份认证

| 产品 | 官方资料或当前代码能确认的授权方式 | 对比含义 |
| --- | --- | --- |
| ToDesk | 临时密码、安全密码等方式，支持不同使用场景 [T6] | 商业远控并非每次都要求有人点击允许 |
| 向日葵 | 识别码请求可由对端确认；验证码可用于直接连接 [S2] | 有人值守协助与持有凭据连接是不同路径 |
| UU远程 | 账号设备列表；协助含验证码、免密确认、双重验证等方式，受平台/版本限制 [U4][U5] | 不能只用一种确认流程概括产品 |
| ZJdesk | 对端 IP 配对与控制请求；默认要求确认，可设置自动允许；代次/序号用于授权后的输入约束 | IP 配对不是账号或设备身份认证，不宜直接等同商业公网访问控制 |

WebRTC 的媒体/数据传输加密，与信令身份认证是不同问题。ZJdesk 当前默认信令并未启用 TLS，也没有完整账号认证体系；适用范围仍应按可信 LAN/VPN 理解。UU 公开 DTLS/AES 不能单独证明其所有连接具备某种特定的端到端身份保证。[U3]

本节只比较已知机制，不对三家产品作安全等级排名。

## 10. 怎样解释当前“光标顺，拖动窗口慢”

最合理的拆分是三种体验：本机指针响应、远端收到输入、控制端看到远端画面。它们可以相差很大。ZJdesk 的本地光标绕开视频回程，所以指针流畅不代表窗口已完成闭环。

结合已有 ZJdesk 历史实验，优先排查接收修复、播放等待与积压，比直接认定“输入慢”更有依据。但这仍不是当前真实拖动的单点定论。

历史 `2026-11-11` 合成标记实验记录：[Z7]

| 配置 | 闭环 p50 | p95 | p99 | 平均呈现帧率 | 最长呈现间隔 |
| --- | --- | --- | --- | --- | --- |
| 接收缓冲 400ms | 458.34ms | 520.34ms | 1152.62ms | 29.42fps | 1832.44ms |
| 接收缓冲 200ms | 278.60ms | 530.98ms | 1014.52ms | 29.16fps | 1056.69ms |

该实验的标记链路是 DataChannel 请求、发送端写入合成帧、接收端 `frameSwapped`，不是物理鼠标到真实桌面再到屏幕发光；当时跨子网但同公网出口，也不是独立公网或 DERP 的全面验收。

降低缓冲后中位改善 179.74ms，但 p95 没有改善。它支持“缓冲对常态延迟有影响”，不支持“改成 200ms 就全部解决”。历史数据也不能用来推算 ToDesk、向日葵或 UU 在同一机器上的表现。

## 11. 对 ZJdesk 的改进建议与验证顺序

以下是建议，**本报告未修改代码或配置**。

| 优先级 | 建议 | 为什么先做 | 可验证的通过条件 |
| --- | --- | --- | --- |
| P0 | 先补齐真实拖动/打字闭环与分阶段时间线 | 防止只优化输入回执或平均帧率 | 同时报告输入回执、呈现闭环 p50/p95/p99、最长冻结和停手后追赶时间 |
| P0 | 分清长期播放偏移、增量 backlog 与无新帧 | 相对基线可能掩盖持续滞后 | 能区分没有数据、等待修复、等待播放、GUI 未呈现四类停顿 |
| P1 | 把排空临时限制和正常帧率上限分开评估 | 当前收紧逻辑可能影响 30fps 恢复 | 短时拥塞后恢复目标帧率，且不带着旧画面长期运行 |
| P1 | 做多档缓冲配对实验，再设计自适应 | 400→200 的历史结果只改善中位 | 在指定网络范围内同时控制尾延迟与冻结，记录有效回退条件 |
| P1 | 测试输入/文件竞争，再决定是否拆通道 | 当前共用可靠有序通道是明确可测点 | 同时复制文件时输入闭环无明显劣化，撤权/按键释放仍可靠 |
| P1 | 验证 NACK/FEC、关键帧和反馈实际工作情况 | 配置存在不等于每次有效或最优 | SDP/统计可证实协商；丢包实验记录恢复时间、冗余与峰值码率 |
| P2 | 评估适合平台的硬件编解码与少拷贝路径 | 提高性能余量，但先确认占用/耗时瓶颈 | 同分辨率/画质预算下比较 CPU/GPU、编码耗时和闭环尾延迟 |
| P2 | 若扩展公网产品，再设计身份、穿透和中转服务 | 当前范围主要是可信 LAN/VPN | 直连失败有受控回退、路径可观测，并完成认证与授权验证 |

不建议从“商业产品支持某编码”直接跳到重写全部媒体栈，也不建议为了减少等待而任意丢弃 VP9 压缩参考帧。先证明当前最主要的等待发生在哪里，再决定改哪一层。

## 12. 后续怎样做公平横测

同一对实体机器、同一方向、同一网络时段，以匹配的分辨率、目标帧率和可比较的画质条件测四款软件。码率设置相同不代表画质相同，无法匹配的条件必须单列。记录客户端版本、套餐/模式、硬件编解码、实际连接路径和显示刷新率。

至少覆盖：

1. **办公闭环**：拖动窗口、连续输入文字、滚动带文字页面；记录可见反馈与停手后是否追赶。
2. **动态负载**：持续运动内容；同时记录细节、帧率和冻结，避免把模糊换流畅当作无代价提升。
3. **网络变化**：明确设置 RTT、抖动、随机/突发丢包和带宽收缩，测试恢复而非只测稳定阶段。
4. **并发业务**：远控同时复制文件，对比空闲传输和文件传输时的输入表现。
5. **授权异常**：断连、失焦、撤权、重新授权与切网后，确认不会残留按键或接受旧会话输入。

若用高速摄影测物理闭环，需要记录拍摄帧率与误差；若用软件标记法，则说明它省略了哪些真实桌面环节。不要将跨机单调时钟直接相减，也不要把多个阶段的 p95 相加当作整体 p95。

本报告没有执行这些横测，也没有验证三家最高帧率、最低延迟、节点覆盖或长期稳定性。当前报告的产出是公开技术证据与源码对照，以及可执行的验证方向。
