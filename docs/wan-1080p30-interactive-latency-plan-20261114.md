### 0.1 项目背景与用户要解决的问题

ZJdesk 是 C++17 / Qt 6.8 桌面协作项目，使用 GStreamer / WebRTC 传送桌面视频，并通过 DataChannel 传递远控输入。当前任务方向为 **Windows 控制 Linux**：Linux 是被控端和桌面视频发送端，Windows 是控制端和视频接收端。

用户要求保留 **1080p30 为最终目标**，改善“本地指针已经跟手，但点击、拖动、打字后的远端画面仍明显滞后”的体验。要验证远端应用响应后的视频结果，不能仅优化鼠标图标，也不能把输入注入回执或接收到任意下一帧当成可见响应。

已有历史测试表明：降低播放缓冲能改善中位延迟，但未解决长尾停顿；当前版本又加入了积压排空机制，尚需检查其真实效果及恢复目标帧率的能力。详细证据、当前实现和待修问题见第 2 节，最终指标见第 3 节。

## 1. 结论与承诺边界

**保留 1920×1080、30 FPS 作为最终目标；先消除点击、拖动、打字之后的陈旧画面与长尾停顿，再验证稳定维持 1080p30。** 本地指针已经跟手，不代表远端应用的响应画面已经跟手。

有依据、应当优先执行的路线是：补齐真实输入闭环测量 → 修正现有积压判定和降帧恢复 → 分档降低接收播放等待 → 对失去解码连续性的情况实施受控恢复 → 最后才按测量结果考虑硬件编解码或控制通道拆分。

对代码中可复现的问题，可以通过回归测试保证修复；对最终跨网体验，必须由实机数据决定。不能在当前证据下承诺“任意网络都无明显延迟”。若网络本身连续断流 500 ms，这 500 ms 内没有新画面可供显示；软件应解决的是恢复后继续播放旧画面、积压越积越多和长期不恢复目标档位。

**本方案的把握来自明确的代码问题、最小改动、逐项对照和可失败的验收，不来自提前宣称成功。** 1080p24、720p30 或高缓冲只能作为临时恢复/降级结果，不能作为完成 1080p30 目标的依据。

## 2. 当前证据：为什么这样改

### 2.1 历史测试证明的问题

| 已有证据 | 能推出的结论 | 不能推出的结论 |
| --- | --- | --- |
| 400 ms 缓冲的标记闭环 p50 / p95 / p99 为 458.34 / 520.34 / 1152.62 ms | 延迟明显，尾延迟需要单独治理 | 不是当前代码的真实点击到画面延迟 |
| 200 ms 对照为 278.60 / 530.98 / 1014.52 ms | 中位数减少约 180 ms，但 p95 没改善 | 不能认定把默认 400 改为 200 就解决问题 |
| 两组最大呈现间隔约 1832 / 1057 ms | 平均约 29 FPS 仍会存在肉眼明显停顿 | 平均帧率接近 30 不等于交互达标 |
| 解码计算 p95 约 3 / 1.9 ms，但解码输出间隔达到 1157 / 833 ms，期间 RTP 仍有到达 | 应先查参考帧等待、播放调度与恢复路径 | 不能直接归因于 CPU 太弱或解码算力不足 |
| 独立 UDP 测试曾出现约 0.5 秒到达空窗，复测未稳定复现 | 必须区分网络断流和软件排队 | 不能把全部停顿都认定为应用缓冲 |

来源：[1080p30 验证](validation-wan-1080p30-20261110.md)、[延迟验证](validation-wan-latency-20261111.md)。这些是较早版本的测试，**不能代替当前 HEAD 的重新测量**。早期 Tailscale 直连记录也不等于已证明独立公网 NAT 下的稳定表现。

### 2.2 当前代码已经做了什么

- `src/media/screen_share.cpp`：编码前原始帧队列容量为 1，允许替换旧原始帧；appsink 容量为 1；UI 使用最新帧邮箱；已有 GCC、码率预算、RTP MTU 控制和关键帧请求机制。
- 同一文件：WAN 默认 `webrtcbin latency=400`，接收 appsink 使用 `sync=true`；支持通过 `ZJDESK_WEBRTC_LATENCY_MS` 选择 30 / 50 / 100 / 150 / 200 / 400 ms。
- `apps/client/video_surface.cpp`：本地鼠标显示、8 ms 移动合并、离散输入前刷新移动，以及实际 `frameSwapped` 统计已经存在。
- `src/remote-control/input_receiver.cpp`：原生输入注入已经进入独立线程，并校验授权、共享代次、控制代次、序号；不要重复建设输入线程。
- `src/media/share_quality.cpp`：已有积压排空逻辑，进入阈值 250 ms，退出阈值 120 ms，排空时降低发送帧率。当前改进应在它的基础上进行。
- `tests/manual/latency_probe.cpp`：已有合成 VP9 标记闭环，时长允许到 7200 秒；现有分析器和后台运行入口可复用。

### 2.3 当前实现与本目标的三个明确冲突

1. **积压不等于绝对延迟。** `videoBacklogMs` 是取帧偏移减去最近 60 秒最低偏移。它能发现相对恶化，却不能证明输入到画面已经足够快；固定 400 ms 等待也可能对应接近零的相对积压。持续较高偏移还可能随旧基线退出窗口而被重新归零。无新帧时，旧偏移也不能代表新的有效观测。
2. **触发太晚、反馈偏慢。** 250 ms 之后才排空、每秒一次反馈，适合控制严重积压，不足以支撑约百毫秒级交互目标。不能仅把阈值调低，因为不可靠的基线会触发误判。
3. **临时抖动会影响长期帧率上限。** `observeBacklog()` 用接收 FPS 的 90% 收紧 `maximumFpsLimit_`，并与显示能力上限共用这一限制。1080p30 的正常档只有 30 / 24；例如积压时上报 30 FPS，90% 为 27，实际只能选到 24。现有稳定窗口不会解除这个上限。这是源码可推导的恢复障碍，尚不能断言本次真实会话一定已发生。

此外，只降至 24 FPS 不保证快速排空：若有约 15 帧积压且接收端每秒只能消费 30 帧，发送 24 FPS 后净排空仅 6 FPS，理论仍需约 2.5 秒；接收端若只能消费 24 FPS，则无法净排空。实际播放时钟和参考帧依赖还可能进一步限制追赶。

## 3. 成功标准与测量口径

### 3.1 真正要测的链路

```text
Windows 产生输入并记 t0
  → 原有控制通道 → Linux 输入线程 → 操作系统 → 远端应用响应
  → 真实桌面采集 → 编码 → 网络 → 修复/解码 → Windows 显示交换并记 t1
交互可见延迟 = t1 - t0
```

两个时间戳均取 Windows 同一个单调时钟，不依赖两台机器时钟相减。Linux 阶段耗时使用 Linux 本机单调时钟；跨机定位使用序号、帧标记和各端局部时长，不把未校准的时间戳直接相减。

`probe_ack` 只证明注入 API 接受请求；“收到下一张视频帧”也不证明这张帧包含输入结果。现有合成标记绕过真实 OS、应用和采集，只用于定位媒体链路，不能作为最终交互验收。

### 3.2 目标门槛

以下是本项目待验证的工程目标，并非已实现指标，也不是所有人的统一感知阈值。

| 项目 | 最终达标条件 |
| --- | --- |
| 正常交互延迟 | 点击、拖动、键入分别计算：p95 ≤ 100 ms、p99 ≤ 150 ms |
| 输入正确性 | 离散按键/按钮不丢失、不乱序、不重复；无卡键、卡拖动；撤销后不执行旧输入 |
| 分辨率与帧率 | 正常阶段始终 1920×1080、目标 30 FPS；动态内容实测加权呈现 FPS ≥ 28.5，至少 99% 完整秒 ≥ 27 FPS |
| 正常阶段长停顿 | 动态场景不得出现超过 200 ms 的呈现空窗；另列最长 10 次延迟与空窗，不能藏在均值里 |
| 故障恢复 | 注入断流结束后 1 秒内恢复新鲜画面为初始目标；网络恢复健康后 30 秒内恢复 1080p30；未达到则不能宣称恢复机制完成 |
| 样本与时长 | 每个核心场景连续运行至少 30 分钟，点击/拖动/键入各至少 1000 个有效观测；至少 3 组独立重复，逐组通过 |
| 主观体验 | 实际显示器上完成点击、连续窗口拖动和连续输入确认；软件指标通过后仍有明显滞后，继续定位 |

故障注入阶段单列统计，不要求在断网期间达到 100 ms，但不能删除故障后的恢复时间。自然发生的网络抖动属于正常长测结果，不能事后剔除。静态桌面无需强制产生 30 次不同内容的更新；帧率门槛用于有持续变化的测试场景，重复显示旧图不能充当新帧。

`frameSwapped` 是软件呈现近似值，不包括完整显示器扫描与像素响应。最终可由用户自行使用高帧率录像同框记录输入动作与显示器变化，复核实际手感；后台隔离桌面测试只作为真实 OpenGL 软件路径证据，不能代替物理屏幕体验确认。该人工项未完成时明确标为待验收，自动执行阶段不弹出前台测试窗口。

### 3.3 网络预算必须满足物理条件

总延迟包含正向输入传输、应用响应/采集等待、编码、回程视频、播放等待、解码与呈现。30 FPS 单次采样等待本身最多约 33.3 ms；网络往返与软件处理还会消耗余下预算。各环节 p95 不能简单相加当作总体 p95。

若实际网络往返已接近或超过 100 ms，就不能保证整体 p95 ≤ 100 ms。此时先改善路由/直连条件或明确报告目标未达成，不能靠隐藏指标或永久降低分辨率宣布成功。30 / 50 ms 的缓冲只是候选值，配置值也不等于最终新增等待，必须读回并测量。

## 4. 实施步骤

### P0：在当前版本上建立真实输入基线

**目的：先确认慢在哪里，并让后续每一项改动都能检验。**

1. 固定两端 commit/源码快照、Qt/GStreamer 版本、Linux 隔离 X11 会话、1920×1080 测试桌面、Windows 隔离 Desktop 内的接收窗口与呈现条件，记录实际软件/硬件编解码器、码率、CPU/GPU 占用。物理桌面只读采集另列结果，不与隔离交互样本混合。
2. 记录 ICE 实际候选对、UDP/TCP、Tailscale direct/DERP、两端网络拓扑、RTT/抖动/丢包、MTU、可用吞吐和同机竞争流量。信令可达不代表媒体直连；无法判定路由时标为未知。
3. 复用现有合成标记探针，对当前 HEAD 先跑 400 / 200 ms，检查旧现象能否重现。保留已有启动、长测、退出码能力，不重新开发一套探针框架。
4. 在 Linux 隔离 X11 桌面内增加测试窗口：只有实际收到鼠标/键盘事件后，才将相应事件序号、文本内容或拖动位置绘制到窗口中；由同一隔离 DISPLAY 的正常桌面采集路径带回 Windows。预置事件脚本用于建立序号对应关系，不能让独立诊断消息直接触发“成功标记”。
5. Windows 测试驱动走原有输入发送路径，关联画面里的结果与真实 `frameSwapped`。点击看状态变化，打字看对应字符出现，拖动看匹配时间位置的轨迹响应；合并掉的连续移动单独统计，不能当作离散输入丢失或悄悄排除尾延迟。
6. 对全部发出事件记录成功、超时、无法匹配、重复和乱序；超时不得从延迟统计中静默消失。分别报告三个动作类型，不能用大量快速鼠标样本掩盖慢点击。
7. 记录原始 JSONL：输入序号/代次、各局部耗时、编码输出间隔、RTP 到达空窗、解码输出间隔、播放偏移、样本新鲜度、等待关键帧、实际 jitterbuffer 配置、appsink sync、FPS、分辨率、控制通道 buffered amount、关键帧大小、GCC/pacer 统计。

**通过条件：** 标记确实来自 OS 输入后的应用绘制；错误关联能被检测；无新帧、超时、窗口卡住也进入报告。仅建立基线不算体验改善完成。

### P1：先修正积压测量与 30 FPS 恢复障碍

**主要文件：** `src/media/screen_share.cpp`、`src/media/share_quality.h`、`src/media/share_quality.cpp`。

1. 明确区分相对积压、绝对输入闭环延迟、无新帧持续时间。给积压数据增加有效性/新鲜度，缺失值不能等同于“已经排空”。
2. 基线只在确认健康、有新样本时更新；持续积压期间不让旧最低值过期自动把积压抹掉。建立新流、时间戳不连续、修改播放策略时显式重建基线并标记暂不可用，不拿重建后的零值直接判定成功。
3. 显示器/协商得到的硬上限与排空使用的临时上限分开保存；临时上限可以解除，硬上限必须保留。这是修复当前 `maximumFpsLimit_` 混用，不扩展成通用策略框架。
4. 短时抖动不能将一次低接收 FPS 认定为永久硬件能力。排空期间的低 FPS 本身由发送端主动限帧造成，不能反复据此降上限。
5. 初始恢复策略：连续 5 秒有效样本显示积压已低于退出阈值且无持续解码空窗后，试升一档；30 FPS 探测窗口先取 5 秒。积压再次增长则回退，至少冷却 10 秒再试；健康网络下以 30 秒内回到 1080p30 为验收目标。所有数字是待调优起点。
6. 保留现有编码前最新帧和 UI 邮箱机制。对发送 pacing 排队、传输栈排队分别观察；`pacedBytes=0` 不代表 libnice、内核或路由器完全无排队。

**必要回归：** 30 FPS 遭遇一次积压后最终能回 30；60 秒持续高偏移不会自行变成健康；无样本/非法数值不触发恢复；对端真实上限 24 时不越限；排空期间不逐次塌到更低档；旧代次反馈不影响新会话。

### P2：按证据降低播放等待，不能只改默认值

**主要文件：** `src/media/screen_share.cpp`、现有探针及分析脚本。

1. 先以当前 400 ms 为稳定参照，再按 200 → 150 → 100 → 50 → 30 ms 逐档比较。每次新会话，保持同一测试内容、路由、码率和版本，避免同时修改多个参数。
2. 用 2～5 分钟短测淘汰明显失败档，再对候选做交替 A/B、至少三组。最终配置必须进入 30 分钟长测，而不能用一次最好的短测定案。
3. 同时读回 `webrtcbin` 和实际 RTP jitterbuffer 的 latency；配置没有下传即判为实验无效。先采用新会话选档，不先开发运行时自适应；只有确认动态修改有效且无参考帧/时钟问题后才考虑运行时调整。
4. 优先保留 `sync=true` 找到可工作的低缓冲范围。如果分段数据仍显示 sink 时钟等待显著，再单独对照 `sync=false`，检查突发交付、UI 覆盖和呈现平滑性。不能把关同步当作已经证明的修复。
5. 若试验 `sync=false`，同步修改分析器的实验配置校验；现有脚本默认要求 sink sync 为真。不能删除读回校验，也不能让工具拒绝合法试验后误报为媒体失败。
6. 编码前原始帧和解码后的完整图像可以保留最新帧；不要在任意压缩 VP9 帧或 RTP 包上加无条件 leaky/drop。`appsink max-buffers=1` 也不能消除它上游的缓冲和关键帧等待。
7. 低缓冲增加修复压力时，先分清丢包修复、参考链断裂和 CPU 饥饿。保持现有 MTU=1100 的 WAN 封包策略，除非新路径证据要求改变；不要靠放大 RTP 包换取表面吞吐。

**通过条件：** 实际输入延迟明显下降、p95/p99 和冻结次数不恶化，最终满足第 3 节。若只有 150/200 ms 能稳定，却过不了交互指标，记录为阶段改善，继续 P3；不宣布完成。

### P3：为停顿设计有边界的恢复

**目的：网络恢复后尽快显示当前画面，避免拖着旧画面慢慢播放。**

先区分三类情况：没有 RTP 到达；RTP 到达但解码无输出；解码有输出但显示无更新。三类问题分别归因，不对所有停顿都请求关键帧或重建连接。

建议在现有逻辑内保留“正常、排空、等待关键帧、恢复观察”几个清楚的状态，不新增独立调度框架。以下数值均为 P0/P2 后需要验证的初始候选：

| 条件 | 动作 | 防止副作用 |
| --- | --- | --- |
| 有效相对积压连续 2 次超过 80 ms；观测间隔约 100～200 ms | 提前进入排空，暂时限帧；按证据收紧码率 | 退出阈值先取 40 ms；不修改显示硬上限，不因一次尖峰立刻改分辨率 |
| 动态内容下，无新解码画面超过约 200 ms 且 RTP 仍持续到达 | 检查丢包与等待参考帧状态；符合条件时请求关键帧 | 请求最短间隔先取 500 ms；计数和记录结果，避免关键帧风暴 |
| 积压约 300 ms 以上或限帧后 500 ms 仍无下降趋势 | 根据瓶颈验证受控跳转到新的可解码关键帧 | 仅在可安全重建参考链的情况下丢弃陈旧压缩数据；不能任意清空 RTP |
| 网络没有包到达 | 标记链路停顿，恢复后观察新帧与积压 | 不通过反复关键帧请求制造额外拥塞，不回放缓存的旧拖动轨迹 |
| 解码正常但 UI 停顿 | 检查邮箱、UI 调度和实际呈现 | 不重建媒体连接掩盖 UI 问题；维持最新完整帧语义 |

“受控跳到关键帧”是本方案中需要原型验证的部分：先确认 GStreamer 1.26.11 的相关元素支持何种刷新方式，在集成试验中验证请求、识别完整关键帧、清理旧参考状态、时间戳连续性和恢复显示。如果无法只刷新接收解码分支而不破坏 WebRTC，则不强行落地，保留限帧排空作为阶段方案并如实标出恢复指标未达标。不得默认整条连接重启，也不得同时撤销正常控制授权。

增加快速观测应轻量、有上限：已有数据复用，只有必要时发送小型恢复反馈；完整统计仍可保持每秒一次。反馈到达延迟也要记录。保留可靠、有序的关键离散输入，不能为了追帧丢弃按下/松开或字符。

**通过条件：** 100 / 300 / 600 ms 断流、轻度随机丢包、UI 暂停分别验证；恢复时间从故障结束起算；恢复到新鲜画面后还应回到 1080p30。无花屏、无关键帧风暴、无无限重启、无长期 24 FPS 锁定。

### P4：防止文件传输拖慢点击和打字

**主要文件：** `src/remote-control/file_clipboard.cpp`、`src/media/screen_share.cpp`。

当前文件与输入共享可靠有序的 `zjdesk-control` DataChannel。文件协议已有读请求/响应节奏，每块原始数据 16 KiB，并非已知的无限发送队列；但 Base64 后约 22 KiB 的消息仍可能在丢包时影响后续控制消息。

先做空闲/文件传输并行对照：如果输入延迟没有明显变化，不扩展通道架构。如果有影响，先限制待发文件响应，在 buffered amount 偏高或交互积压时暂缓下一块，并让尚未进入 SCTP 的离散输入优先。不能“插队”已经发到可靠有序通道里的消息；暂停时仍需正确处理超时、取消和断线。

只有上述措施仍不达标，再增加独立可靠文件通道，并处理旧版本协商/回退。多个 DataChannel 仍共享 SCTP 和底层链路，是否缓解跨流阻塞还取决于实现和消息交错能力，必须实测；不能把“拆通道”当作带宽与拥塞隔离。非可靠鼠标通道不属于第一轮方案。

**通过条件：** 文件并行传输时点击/键入仍满足交互门槛；文件完整性、取消、重连和输入顺序无回归。允许降低文件吞吐来保留交互体验。

### P5：仅在证据指向时引入硬件编解码

历史解码耗时只有几毫秒，第一轮没有充分理由迁移编解码器。Windows RTX 3060 在接收侧，也不会自动加速 Linux 发送端的编码。

如果真实桌面测试显示编码持续超过帧预算，或解码/转换确实占据主要延迟，再独立验证 Linux 可用的硬件编码与 Windows 可用的硬件解码。先检查实际插件、驱动、低延迟配置、像素格式、码流兼容性、关键帧行为和纹理上传成本；硬件失败必须回退现有软件路径。

此阶段不预先承诺换 H.264/AV1、GPU 零拷贝或引入新的依赖。只有在现有链路不能通过目标、且独立 A/B 证明收益时，才形成单独变更。硬件方案同样必须通过文字清晰度与连续拖动验证。

## 5. 验证安排与停步条件

| 阶段 | 要验证的结果 | 不满足时的下一步 |
| --- | --- | --- |
| P0 基线 | 真实输入与画面能正确关联；两端环境与路线明确 | 修测量，不进行“指标优化” |
| P1 排空/恢复 | 相对基线不会掩盖持续积压；短抖动后可回 30 FPS | 修状态与单测，不引入更多自适应参数 |
| P2 缓冲 | 更低延迟且尾部/冻结未恶化；读回符合试验配置 | 找到保守候选并进入 P3，不盲降到 30 ms |
| P3 故障恢复 | 受控故障后迅速回到当前画面、随后回到目标档 | 区分网络/参考链/UI，不能直接跳到更换编解码器 |
| P4 并行业务 | 文件传输不破坏交互 | 先背压，再考虑单独文件通道 |
| 最终验收 | 三类交互、动态 1080p30、长测和实际手感同时通过 | 报告具体未达项与外部限制，目标保持未完成 |

必要测试分层：

- 单元测试：扩展 `tests/unit/tst_core.cpp`，覆盖暂时上限恢复、硬上限约束、基线与缺失样本、迟滞与冷却；文件背压变动对应扩展 `tests/unit/tst_file_clipboard.cpp`。
- 媒体集成：扩展 `tests/integration/tst_media.cpp`，覆盖配置实际读回、关键帧恢复和停止/重启生命周期；实际 GStreamer 能力缺失应标记缺失，不能伪造通过。
- UI 回归：在真实桌面运行相关测试，验证移动与按钮顺序、组合键、失焦释放、授权撤销、缩放坐标、最新帧呈现。不得用 offscreen 结果冒充实际 OpenGL 验证。
- 分析器：扩展 `tests/scripts/test_analyze_wan_latency.py`，验证超时纳入失败、无呈现整秒保留、无效关联被拒绝、分动作统计、长测采样数量和实验配置校验。
- 双机实测：先固定当前可用网络做 A/B，再在实际独立网络环境重复；direct、DERP、UDP/TCP 分开报告。需要的路径不可用则明确写未验证。
- 应用操作：在隔离桌面内验证窗口拖动、终端连续输入、编辑器选区/滚动、小字体阅读；输入法场景单列，应用/输入法本身耗时仍计入实际体验。物理桌面手感由用户后续确认，自动任务不能借此要求而显示测试窗口，也不能将其记作已完成。

测试先聚焦改变的模块，再按实际改动运行项目要求的回归。Windows 使用 `build.ps1`，Release 部署遵循 `-Preset windows-release -Deploy`；Ubuntu 遵循现有构建入口与 Qt 6.8 / GCC11 基线。两端代码版本必须配套。当前文档编写不等同于已运行上述测试。

## 6. 交付拆分与回滚

建议以可单独评审的改动逐步交付：

1. **测量与回归**：复用现有工具，新增真实输入窗口、关联与报告；不改变用户默认策略。
2. **积压/恢复修正**：修复基线有效性和临时/硬上限混用，证明 30 FPS 恢复；保留既有稳定策略作对照。
3. **低延迟播放及必要恢复**：先落地通过对照的固定候选，再落地经证明必要的关键帧恢复；不同实验分开验证。
4. **并行传输与最终验收**：有证据才改文件调度；整理三组长测与实际体验结果。只有最终门槛通过才更改默认远控策略。

默认策略变更应限定在本任务的远控共享场景。若需要区分观看与控制，由 `SessionCoordinator` 传递语义到媒体层，UI 不直接设置网络、媒体或系统输入行为；会议和普通观看不顺带修改。

回滚时区分两件事：`ZJDESK_WEBRTC_LATENCY_MS=400` 并重建会话可以恢复缓冲对照值，但不能撤销其他代码改动；需要完整行为回滚时，恢复已记录的两端构建与配置。400 ms 是可用性回退，不是低延迟验收成功。

新策略发生花屏、参考链持续失效、按键/按钮顺序异常、撤销后旧输入执行或冻结显著增多，停止扩大部署，保留失败日志并回退对应变更。不要同时回退无关的既有功能。

源码变更涉及架构行为时同步维护 `docs/architecture.md`、`docs/handoff.md`、`docs/roadmap.md`。本次只新增计划文档，不将尚未实现的行为写成当前功能。历史[低延迟计划](wan-1080p30-low-latency-plan-20261111.md)保留为背景；本任务以本方案的“真实交互优先、最终恢复 1080p30”与验收口径为准。

## 7. 最终报告必须提供什么

- 两端版本、实际路由、配置读回、真实分辨率/FPS、编码器/解码器以及完整运行时长。
- 每组测试分别列出点击/拖动/键入的样本数、成功率、p50/p95/p99、最大值、超时和前十次最慢事件，不能只汇总最好一组。
- 呈现加权 FPS、完整秒分布、最大空窗、降级次数/时长、关键帧请求次数、回到新鲜画面与回到 1080p30 的时间。
- 与同一 HEAD 基线的对照，说明收益来自哪项修改，是否牺牲清晰度、带宽或文件吞吐。
- 实机输入、GStreamer、真实 OpenGL、物理显示器确认、Ubuntu 与云端 CI 的完成/未完成状态分别列出。
- 原始日志放 `build/` 下的独立测试目录，不提交生成物；将可复现条件与结论写入验证 Markdown。

**完成判定：真实点击、拖动、打字的响应画面达到门槛，且正常网络下稳定恢复并保持 1080p30。** 若只改善本地鼠标、平均 FPS 或合成标记中位数，任务仍未完成。
