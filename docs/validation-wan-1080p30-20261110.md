# 跨局域网 1080p30 验证

## 实现范围

`NetworkSetup` 验证成功后绑定本机和对端地址。屏幕共享启动时，Tailscale 源地址或跨本机网卡子网的对端地址自动选择 WAN 档位，也可通过 `ZJDESK_SHARE_WAN=1` 显式选择。

- 保持源画面比例，最高 1920×1080 / 30 fps，小尺寸源画面按原尺寸编码。
- VP9 profile 0 / I420，GCC 最低 128 kbps、初始 4 Mbps、默认最高 12 Mbps，编码预算预留 20% 传输余量。
- `ZJDESK_WEBRTC_MAX_BITRATE` 接受 128000..40000000 bit/s 的显式预算。预算不能作为网络线速硬限速保证。
- `ZJDESK_SHARE_LOW_BANDWIDTH=1` 优先选择 960×540 / 15 fps、默认 800 kbps 的保守档位。
- 编码或对端有效帧率不足时自动降档，稳定后恢复。传输额外延迟和丢包参与码率调整。降档前区分"编码端跟不上"和"链路瞬时抖动"：前者连续 2 个统计窗口即降档，后者只在连续 4 个窗口都慢时才降档；恢复需要连续 15 个稳定窗口且传输额外延迟低于 60 ms。
- WAN 接收端让 appsink 按 GStreamer 时钟交付帧，减少突发解码帧覆盖 GUI 邮箱。用户选择优先流畅度后，WAN 默认接收缓冲提高至 400 ms，相比 200 ms 配置增加约 200 ms 画面延迟。诊断值支持 30、50、100、150、200 和 400 ms。
- WAN 和保守档的 RTP 封包上限为 1100 字节，为 1280 MTU 路径上的 RTP 扩展、修复和 SRTP 开销留出余量。

## 环境与方法

Windows 为 i7-11800H、16 GB 内存、Intel UHD / RTX 3060 Laptop，1920×1080 桌面，Qt 6.8.3、GStreamer 1.26.11、MSVC 2022 Release。连接 OnePlus 5 GHz 手机热点，用户确认使用蜂窝流量。

Ubuntu 22.04 为 i7-1355U、32 GB 内存，真实 Xorg 1920×1080 桌面，Qt 6.8.3、GStreamer 1.26.11、GCC 11 Release。独立源码与构建位于 `/home/orbbec/ZJdesk/wan-1080p30-20261110`，依赖装在 `~/.local/opt/zjdesk-deps`，运行必须经该目录的 `wan-linux-run.sh` 包装脚本设置 Qt / GStreamer 环境；直接调用二进制会落到系统 GStreamer 1.20 插件，出现 `组件“webrtcbin”中找不到属性“name”`。Xorg 在 vt2、socket 为 `:1`、cookie 为 `/run/user/1000/gdm/Xauthority`。

Windows Tailscale 地址为 `100.122.3.99`，Linux 为 `100.87.60.58`。Windows 服务最初处于 NoState，用户使用管理员 PowerShell 重启后恢复。系统 ping 短测约 13～37 ms，Tailscale ping 显示 direct，个别探测超过 100 ms。Linux 观察到对端 direct 端点为 `10.11.49.76:41641`，因此公网及热点内部具体路由只能按实际观测记录。热点续租后 Windows WLAN 地址变为 `10.112.150.8`（此前为 10.112.150.119），活动网卡只有 WLAN 与 Tailscale。

双机使用 `zjdesk-control-probe` 走正常网络验证、会话、屏幕共享与输入通路。发送端采集真实桌面，控制端通过 `--present` 使用产品 `VideoSurface` 原生 OpenGL 渲染并回传实际绘制帧数。接收、解码与实际 frameSwapped 分别记录。

用户要求测试 UI 全部后台后，Windows 图形测试使用独立原生 Desktop，通过 `CreateDesktopW` 和 `STARTUPINFO.lpDesktop` 启动，保持用户当前桌面；探针复用该方式（`tests/scripts/run-probe-background.ps1`）。双机探针使用 `--media-only`，发送端采集当前桌面，跳过测试窗口和键鼠注入。Windows 接收端在独立桌面绘制，Linux 接收端只记录解码 / 交付，不显示窗口。因此 Linux 侧数据证明解码与交付，不证明 Linux 实际绘制。

## MTU 与独立 UDP 诊断

两端 Tailscale 接口 MTU 为 1280。修复前 `rtpvp9pay` 使用默认 1400 字节上限，Linux `strace` 记录发往 Windows Tailscale 地址的 21,359 次成功 UDP `sendmsg`，最大负载 1443 字节，其中 20,447 次超过 IPv4 无分片 UDP 负载上限 1252 字节。修改 RTP 上限为 1100 后，58,200 次发送最大负载为 1213 字节，超过 1252 字节的次数为零。

以 1100 字节均匀 UDP 数据独立短测 Linux 到 Windows，1、2、4、8 Mbps 各约 8 秒，丢包率分别约为 0%、0.33%、0.47%、0.43%，最长收包空档分别约为 250、328、234、156 ms。该数据支持增加接收缓冲的对照试验。用户确认 Windows 一直未连接 EasyConnect，具体底层路由按实际观测记录。

长时间容量对照（`--media-only` 之外的全新独立脚本，1100 字节 500 pps ≈ 4 Mbps）：

- Linux → Windows 240 秒：丢包 15 包（0.014%），单向延迟最大 546.8 ms，集中在第 80.3 秒，约 0.5 秒的数据被压后一次性涌出；超过 60 ms 的秒只有 9/240。
- 同方向 240 秒复测：最大延迟 99.4 ms，最长收包空档 63 ms，不丢包。
- Windows → Linux 240 秒：零丢包，最大延迟 71.8 ms，最长收包空档 63.3 ms。
- 结论：链路两个方向都能稳定承载 4 Mbps 级别的共享码率；约 0.5 秒的停顿只在 Linux → Windows 方向偶发（约 4 分钟 0～1 次），属手机热点下行或 Windows Wi-Fi 接收侧抖动，不是应用编码问题，也不是 MTU / 分片问题。

## 根因分析

修复前的失败样本（Linux 发送、Windows 接收，`ZJDESK_WEBRTC_MAX_BITRATE=2000000`，119 个统计窗口）：

- 前 79 秒为 1920×1080 / 30，呈现间隔约 36～38 ms，丢包 0。
- 第 07:15:59 窗口出现一次 0.4～0.7 秒的接收侧停顿：`transportExcessMs=670`、`controlRttMs=678`。同窗口 `encoderBitrate` 从 1600000 降到 616247，即 `ShareQuality::observeNetwork()` 连续触发码率下调。
- 发送端 `fps` 全程保持 29.9～30.9，编码端从未掉帧；抖动全程 0.2～11 ms，累计丢包仅 135（0.1～1.8%）。
- 接收端连续 2 个窗口低于目标 85%（15 fps 对 30 fps），旧策略立即降一档；改 caps 触发重协商，又造成 1.4～3.3 秒的新停顿，再触发下一次降档。
- 结果：1080p30 → 1080p24 → 900p24 → 720p24 一路下行，最终 640×360，TCP 对照同样停顿和降档。

即：链路本身没有持续拥塞，问题在于**一次 0.5 秒的瞬时停顿被当成长期能力不足**，且降档重协商本身产生新的停顿，形成正反馈。

## 自适应阻尼

`src/media/share_quality.cpp` 的三处修改（不改编码器、不重建管线）：

- `observe(encodedFps, receivedFps)`：`starved = actual < fps * 0.85` 且 `encoderStarved = starved && encodedFps < fps * 0.85`。编码端饥饿时仍连续 2 个窗口降档；编码正常而接收掉帧时要求连续 4 个窗口，因为缩短尺寸无法修复链路停顿。
- 恢复条件从"连续 30 个稳定窗口且额外延迟 < 30 ms"改为"连续 15 个窗口且额外延迟 < 60 ms"。原阈值高于本链路 SCTP 往返抖动（常 150～200 ms），降档后实际永不恢复。
- `observeNetwork()` 的延迟门限从 80 ms 提高到 250 ms，触发从连续 2 个窗口改为连续 3 个；"健康"门限从 20 ms 放宽到 60 ms。原门限低于该链路基线抖动，码率会被持续下调。

同步更新 `tests/unit/tst_core.cpp` 的降档/恢复窗口次数，并把 `slowReceiverChangesFrameRateAndResolutionWithoutRestart` 超时从 45 s / 30 s 放宽到 60 s / 45 s（降档阶梯现在每档 4 秒稳定期加 4 个窗口）。

## 双机验收结果

四轮真实双机测试，均未设置 `ZJDESK_WEBRTC_MAX_BITRATE`（WAN 默认 12 Mbps），接收缓冲 400 ms，Windows 接收端在独立桌面绘制。

| 方向 | 时长 | 统计窗口 | 分辨率 / 目标帧率 | 交付 FPS | 长间隔 | 丢包 |
| --- | --- | --- | --- | --- | --- | --- |
| Linux → Windows | 150 s | 149 | 全程 1920×1080 / 30 | p50 29.9，最低 12.0（1 窗） | 最大 672.5 ms（1 窗） | 39 |
| Linux → Windows | 300 s | 279 | 全程 1920×1080 / 30 | p50 29.9，最低 27.9 | 最大 73.7 ms | 0 |
| Windows → Linux | 150 s | 149 | 全程 1920×1080 / 30 | p50 29.9，最低 2.0（1 窗） | — | 0 |
| Windows → Linux | 300 s | 277 | 全程 1920×1080 / 30 | p50 29.9，最低 1.0（2 窗） | — | 1 |

关键点：

- 四个样本都没有出现任何档位切换，质量阶梯只有 `1920x1080@30`。
- 300 秒反向样本中，Windows 发送侧观测到一次 `transportExcessMs=628`，Linux 接收侧因此出现 2 个慢窗口（最低 1.0 fps），旧策略必然降档，本轮保持 1080p30——阻尼策略按设计生效。
- 150 秒正向样本的 672.5 ms 呈现间隔未引发降档；300 秒正向样本连超过 200 ms 的窗口都没有。
- Windows 接收端呈现帧率与交付帧率一致（`presentedFps` 有数据），说明解码到 OpenGL 绘制的整条链路在独立桌面下同步。

## 复现命令

Linux 作发送端、Windows 作接收端：

```
# Linux
bash wan-linux-run.sh ./bin/zjdesk-control-probe --listen --server ws://100.87.60.58:8765 \
  --host --media-only --peer 100.122.3.99 --seconds 300 --output output/wan3-linux-host.jsonl

# Windows（独立桌面）
tests\scripts\run-probe-background.ps1 -Arguments "--server ws://100.87.60.58:8765 --peer 100.87.60.58 --media-only --present --seconds 300 --output output/wan3-windows-controller.jsonl"
```

反向把 `--host` 与 `--server` 地址对调，Linux 端去掉 `--present`。`--host` 与 `--media-only` 组合的结果判定是 `frames >= 30`，因此发送端不会因键鼠断言失败；验收看 JSONL 统计而不是退出码。分析用 `build/analysis/summarize.py`。

## 边界

- 单次样本最长 300 秒，尚未完成 30～60 分钟动态桌面压力、细字画质、实际拖动 / 放大与热点长时间路径稳定性验收。
- Linux 侧只验证解码与交付，未验证 Linux 实际绘制；Linux GUI 组需在真实桌面单独运行。
- `windows-runtime-integrity` 需在非提权会话复验。
- `conferenceUsesSelectedLocalAddress` 的偶发失败需单独排查，当前证据指向 libnice 绑定时机而非屏幕共享链路。
- 0.5 秒级链路停顿在当前链路上仍会偶发（约 4 分钟 0～1 次），阻尼策略把它挡在降档之外，但无法消除停顿本身带来的画面卡顿。
