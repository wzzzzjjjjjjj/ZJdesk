# ZJdesk 跨局域网 1080p30 低延迟优化方案

编制日期为 2026-11-11。本文依据当前 `ZJ-desk` 代码与 2026-11-10 验证记录制定，供后续实现、后台测试和验收使用。文中的阶段、参数候选和验收阈值属于拟定工程目标，效果由新一轮实测确定。

代码核对基线为 `bebb3c129b92`。每轮实施与验证报告另外记录当轮提交号和工作区差异。

## 1. 优化目标与交付范围

在 Windows 与 Ubuntu 不同局域网、通过可达的 WebRTC 路径远程控制时，维持 1920×1080、目标 30 fps 和当前 VP9 4:2:0 画质基线，降低从操作发出到远端变化返回画面的时间。

实施按以下顺序推进。

0. 确认当轮 Tailscale 路径、RTT 与到达空档，按 direct 和 DERP 分组开展对照，见 7.1。
1. 补齐延迟测量与后台测试可靠性，建立 400 ms 基线。
2. 对照 200 ms、150 ms 固定接收缓冲，选择满足画面验收的最低档。
3. 根据固定档实测决定是否实现自适应接收缓冲。
4. 依据分段耗时，处理发送排队、控制消息竞争或编解码瓶颈。
5. 完成双向连续长测、故障恢复与回退验证后，确定部署默认值。

所有测试 UI 均在后台执行。Windows 使用独立原生 Desktop，Linux 使用无窗口探针，或在事先验证的独立后台图形会话中执行图形验证。后台图形测试必须记录实际渲染后端与帧交换证据。

本方案交付时已经完成代码和历史证据核对。后续各阶段的实现结果、实际延迟和通过结论由独立验证报告记录。

### 2.3 可以验证的收益假设

把接收缓冲配置从 400 ms 调到 200 ms，可减少 200 ms 的配置预算。调到 150 ms，可减少 250 ms 的配置预算。实际操作到画面的改善还取决于网络到达时间、重传、采集、编码和呈现调度。

30 fps 对应约 33.3 ms 的画面更新间隔。每帧从采集到显示的年龄需要另外测量。缓冲配置、输入回执和 FPS 各自描述不同环节。

### 2.4 延迟预算模型

预算分析先建立以下时间线，再按实际计时点划分区间。

```
输入发出 → 远端接收并执行 → 应用状态变化 → 采集
        → 转换和编码 → 传输与修复 → 解码与播放调度
        → 颜色转换和邮箱 → frameSwapped → 屏幕实际输出
```

| 区域 | 现有观测 | 使用方式 |
| --- | --- | --- |
| 采集至编码入口 | `captureToEncoderTiming` | 核对时间点、帧匹配和未匹配数量 |
| 编码或解码 | `codecTiming` | 按发送端或接收端分别解释 |
| 输出连续性 | `outputGapTiming` | 记录相邻输出间隔 |
| 网络与修复 | RTT、丢包、到达间隔、GCC 和关键帧事件 | 和画面停顿按时间关联 |
| 解码至接收出口 | `decodedToSinkTiming`、`sinkToPullTiming` | 结合 probe 位置区分转换和时钟等待 |
| 邮箱至交换完成 | `mailboxTiming`、`presentation` | 对应同一帧，分析队列和 GUI 调度 |
| 屏幕实际输出 | 后续光学或显示链路测量 | 与 `frameSwapped` 的软件终点分开报告 |

400 ms 是接收管线配置值。配置变化的理论预算收益与闭环测得的实际收益分别列出。

分段时间线标明每个计时区间的起止点与重叠关系，端到端结果使用闭环直接测得。GStreamer 时钟调度会同时受 pipeline latency 与 jitterbuffer 影响，需要避免重复计算。输入至画面反馈包含控制向和视频返回向的网络路径，单程估计需要说明对称性假设及误差界。

### 2.5 接收缓冲与重传的取舍

当前管线配置 NACK 与 ULP_RED 修复。缩短缓冲会减少丢包检测、请求重传与解码的可用时间，需要同时观察迟到丢帧、修复成功率和关键帧恢复。

候选档位应比较剩余播放期限与丢包检测、媒体重传往返、解码余量之和。控制通道 RTT 可提供辅助参考，媒体路径统计和实际迟到事件决定修复效果。

RTT 较高或到达空档较大的路径采用更谨慎的缓冲候选。direct 和 DERP 两类路径分别验收，记录各自适用的最低档位与恢复能力。

### 2.6 关键帧周期与码率尖峰

软件编码配置 `keyframe-max-dist = fps × 5`，30 fps 下对应最多 150 帧的周期限制。实际关键帧还受请求和输入节奏影响。以 `keyframes`、`maxKeyframeBytes` 与收发速率的同一时间线分析突发。

缩短关键帧周期可能增加平均开销与发送突发。相关实验同时验证修复时间、关键帧大小、GCC 队列及图像质量，再决定是否采用。

## 3. 指标定义与测量方法

### 3.1 指标清单

| 指标 | 测量起点与终点 | 采集要求 |
| --- | --- | --- |
| 输入确认往返 | 控制端发出输入至收到注入确认 | 复用 `inputProbeAcknowledged`，同时记录注入耗时 |
| 测试指令到画面反馈 | 测试控制指令发出至匹配标记实际 `frameSwapped` | 全程用控制端单调时钟计算 |
| 真实操作到画面反馈 | 原生输入发出至应用可见状态变化实际呈现 | 包含正常输入后端、桌面采集、编解码与显示 |
| 采集至编码入口 | 同一发送进程中的对应时间点 | 复用已有分段诊断，核对帧关联是否成功 |
| 编码和解码耗时 | 对应 codec 输入和输出 | 记录 p50、p95、p99、最大值及未匹配数量 |
| 解码后等待 | 解码输出至 appsink、邮箱和绘制 | 复用 `decodedToSinkTiming`、`sinkToPullTiming`、`mailboxTiming` 与呈现统计 |
| 实际绘制 FPS | 唯一新帧的 `frameSwapped` 计数差除以实际时间 | 原样保留低帧率和零帧窗口 |
| 画面长间隔 | 相邻新画面实际呈现的单调时间差 | 汇总超过 100 / 200 / 500 ms 的次数 |
| 传输排队 | GCC 估计、`pacedBytes`、DataChannel 缓冲和实际收发 | 同时记录变化过程和峰值 |
| 图像年龄 | 发送采集至接收呈现 | 跨机计算须提供时钟偏移及误差界 |

`controlRttMs` 是 DataChannel 探针往返时间。`transportExcessMs` 是高于近期基线的往返额外时间。解释这些指标时必须保留其起止点。跨机两个单调时钟相减前，必须完成偏移估计与不确定度分析。

### 3.2 后台闭环标记测量

先补一个可重复的测试控制闭环。

1. 控制端发送带递增序号的测试指令，并记录本地单调时间 `t0`。
2. 被控端的专用动态测试源将序号绘制成高对比度图案，经过正常编码和 WebRTC 链路返回。
3. 控制端在解码帧中识别序号，绑定到对应的待绘制帧。
4. 在该帧实际 `frameSwapped` 后记录 `t1`，保存 `t1 - t0`。
5. 统计超时、未匹配、被覆盖、重复及成功样本。超时比例随延迟分位数一起交付。

该方法可在全部 UI 后台的条件下验证控制通道到画面呈现的闭环。结果命名为“测试指令到画面反馈”，并列明测试源覆盖的路径。

真实操作验收增加原生输入和真实桌面采集。目标窗口、输入作用范围与采集范围必须位于同一隔离会话。现有 `CreateDesktopW` 包装器已经验证隐藏绘制，仍需额外证明原生输入和 D3D11 采集可以安全覆盖同一隔离目标。该条件未完成时，真实操作延迟一项标记为待验收。

Windows 后台桌面的系统输入测试须先验证输入隔离，确保测试事件只作用于专用目标。Linux 图形验证也须先确认独立会话及实际图形后端。当前无窗口 Linux 探针继续承担解码与交付验证。

### 3.3 分位数与数据完整性

现有 `FrameTiming` 在 100 ms 以上使用溢出桶，并以最大值作为保守分位界。长达数百毫秒的端到端延迟需要单独保存测试原始样本，再离线计算 p50 / p95 / p99。现有分段直方图继续用于其覆盖范围内的局部耗时。代码依据见 [frame_timing.h](F:/projects/ZJdesk/src/media/frame_timing.h:29)。

每轮固定预热 20 秒。性能稳态统计从预热结束起算，同时独立保留启动阶段报告。预热后的断流、重连、零帧窗口与降档全部进入失败和长尾统计。缺少日志的时间段记为缺失，输出实际覆盖率。

标记频率初始设为每秒 1 次。短测每轮至少取得 200 个有效闭环样本，连续长测至少取得 1000 个样本，并报告超时和丢样本数量。p99 同时列出样本总量和最慢样本，便于评估有限样本的影响。

至少保存以下信息。

- 提交号、工作区差异标识、运行库版本、硬件与电源状态。
- 测试方向、缓冲请求值和实际读回值、目标分辨率及帧率。
- 起止单调时间、有效样本数、采样间隔和日志覆盖率。
- 本机与对端地址、实际 ICE 传输、Tailscale direct / relay 观测时间。
- 编码 / 解码 / 交付 / 实际绘制计数、码率、丢包计数增量和队列峰值。
- 画面反馈延迟原始样本、超时数量、最大停顿及事件时间线。

### 3.4 接收端播放时间线诊断

在 appsink 拉取帧时，可增加同进程的播放时间线偏移诊断，用于对照缓冲档位与调度变化。实现时先检查时间戳有效性，并把 buffer PTS 通过当前 segment 转换为 running time。

拟记录以下量。

```
pipelineRunningTime = pipelineClockNow - pipelineBaseTime
bufferRunningTime = segmentToRunningTime(bufferPts)
playoutTimelineOffset = pipelineRunningTime - bufferRunningTime
```

该偏移描述接收管线内的时间关系。它的参考原点、pipeline latency 与 RTP 时间映射需要核对后解释。端到端画面年龄由闭环标记或完成时钟关联的采集时间戳另行测得。

- 实施位置为 `src/media/screen_share.cpp` 的 appsink 拉取位置，靠近 `sinkToPullTiming_`。诊断命名明确区分时间线偏移、播放迟到和端到端年龄。
- 同时保存 PTS 有效性、segment、pipeline latency 及帧关联，排查状态切换与重建期间的异常。
- 大于 100 ms 的样本采用独立统计范围或测试原始记录。存在负偏移时保留符号并解释，不直接套用只接受非负耗时的统计器。

该诊断与闭环标记、解码及交换完成的时间线联合使用，用于解释实际收益与配置预算差异。

## 5. 阶段 P1 —— 固定缓冲对照

### 5.1 对照矩阵

| 组别 | 接收缓冲 | 用途 | 推进条件 |
| --- | --- | --- | --- |
| A | 400 ms | 当前流畅度基线 | 每组测试均安排相邻基线 |
| B | 200 ms | 首选低延迟候选 | 先完成双向短测 |
| C | 150 ms | 进一步降低等待 | B 通过画面和延迟门槛后进入 |
| D | 100 ms | 稳定低抖动路径的探索 | C 通过，且网络尾部空档有足够余量 |

每个方向至少安排 3 组配对短测。顺序采用 A→B、B→A、A→B，降低热点状态随时间变化造成的偏差。150 ms 候选采用同样的配对方法。

C / D 两档先在低 RTT、低抖动路径探索。中继路径按自身修复期限和实际丢包另行对照，形成该路径的候选结论。

所有组使用相同的源画面、场景、VP9 参数、码率策略与目标帧率。首轮使用产品默认预算。显式 2 / 4 Mbps 上限作为后续独立实验变量，单独出表。

每轮开始记录 Tailscale 路径与网络探测结果，运行中记录路径切换。WebRTC 的 ICE 传输和 Tailscale 的 direct / DERP 分层记录。发生路径切换的样本保留完整时间线，并补做路径稳定的对照。

开始前核对进程继承的 `ZJDESK_SHARE_LOW_BANDWIDTH`、`ZJDESK_SHARE_WAN`、`ZJDESK_WEBRTC_GCC`、`ZJDESK_WEBRTC_MAX_BITRATE` 和 `ZJDESK_WEBRTC_LATENCY_MS`，把生效值写入报告。配对样本的固定条件保持一致，编排器在结束后恢复环境。

### 5.3 当前可用的短测命令模板

以下使用既有隔离目录和历史 Tailscale 地址。执行前核实当前地址、SSH 可达性、Qt / GStreamer 环境及 8765 端口归属。Linux 命令由 SSH 后台编排启动，Windows 命令在项目目录执行。两端进程须重叠运行，接收端在发送端就绪后 30 秒内启动。

Linux 发送进程以 300 秒运行。该命令使用无窗口、无键鼠注入模式。

```bash
cd /home/orbbec/ZJdesk/wan-1080p30-20261110
env ZJDESK_SHARE_WAN=1 \
  bash ./wan-linux-run.sh ./bin/zjdesk-control-probe \
  --host --media-only --listen \
  --server ws://100.87.60.58:8765 \
  --peer 100.122.3.99 \
  --seconds 300 \
  --output output/latency-a-linux-host.jsonl
```

Windows 接收进程以 260 秒运行，前 20 秒固定预热，剩余阶段用于短测。每次运行选择一个组别及唯一报告名。

```powershell
$taskPreviousLatency = $env:ZJDESK_WEBRTC_LATENCY_MS
try {
    $env:ZJDESK_WEBRTC_LATENCY_MS = '200'
    & .\tests\scripts\run-probe-background.ps1 -Arguments '--server ws://100.87.60.58:8765 --peer 100.87.60.58 --media-only --present --seconds 260 --output output/latency-b-windows-controller.jsonl'
} finally {
    if ($null -eq $taskPreviousLatency) {
        Remove-Item Env:ZJDESK_WEBRTC_LATENCY_MS -ErrorAction SilentlyContinue
    } else {
        $env:ZJDESK_WEBRTC_LATENCY_MS = $taskPreviousLatency
    }
}
```

400 ms 与 150 ms 分别替换接收端环境变量及报告名称。当前代码在共享接收管线启动时读取该变量，因此每个对照样本重新建立会话。

反向测试由 Linux 提供独立后台信令进程，Windows 在隔离 Desktop 中作为发送方，Linux 通过 SSH 运行无窗口接收进程。Linux 接收进程的环境中设置缓冲值。自建信令进程记录 PID、绝对运行目录与命令行，测试结束核对身份后清理。反向样本的 Linux 数据按解码与交付口径报告，实际绘制需要独立后台图形会话证据。

## 6. 阶段 P2 —— 自适应接收缓冲

### 6.1 进入条件

至少一个低于 400 ms 的固定档通过双向对照，且测量能够区分网络数据到达、解码等待与实际绘制停顿。若固定 200 ms 已满足目标，可先交付固定档候选并继续积累长测数据。

### 6.2 控制策略候选

下列值用于首轮实现实验，后续根据 P1 数据校准。

| 项目 | 候选规则 |
| --- | --- |
| 档位 | 首轮采用 150、200、400 ms，最低档由 P1 结果确定 |
| 启动值 | 选择 P1 已通过的最低稳态档 |
| 观察窗口 | 10 秒滚动窗口，使用本地单调时间 |
| 升档信号 | 经确认的迟到丢帧、接收空档与解码输出中断同时分析 |
| 升档触发初值 | 2 秒内至少 3 次因迟到产生的帧失效，且发送编码保持正常 |
| 降档条件初值 | 连续 60 秒健康，实际绘制与迟到率通过门槛 |
| 冷却期 | 升档后至少观察 10 秒，下降每次一级并重新开始健康计时 |
| 上界 | 400 ms，持续链路故障进入明确的退化状态 |
| 显式配置 | `ZJDESK_WEBRTC_LATENCY_MS` 固定指定时采用固定档并输出生效模式 |

迟到原因需要来自可核实的 jitterbuffer / 帧关联诊断。现有 `jitterMs` 与 SCTP 额外 RTT 作为辅助证据，与视频到达尾延迟分别记录。

### 6.3 线程与时序要求

- 调整由媒体 worker 执行，所有异步反馈带共享代次并校验有效性。
- 先验证 GStreamer 1.26.11 在当前状态下修改 `webrtcbin latency`、向现有 jitterbuffer 传播及重新计算 pipeline latency 的实际行为。
- 记录修改请求值、读回值、起止时间和短期绘制间隔，确认应用成功后更新生效状态。
- 一次调整完成并取得反馈后，再处理下一次请求，限制反馈队列长度。
- 缩短缓冲时验证 PTS、播放时钟和待呈现帧的连续性。过时画面的合并限定在可安全处理的已解码层。
- VP9 压缩帧按参考依赖恢复。损坏参考链路沿现有关键帧恢复机制处理。
- 画质自适应和缓冲控制采用独立统计，结合发送编码能力判断退化原因。

若运行期调整需要重建管线且引入显著停顿，P2 先采用“会话开始选择档位”，把连续运行期调整作为后续独立工作项。

### 6.4 恢复验证

在测试专用路径中分别注入 100 / 300 / 600 ms 的短时数据到达停顿，观察档位、丢帧、恢复时间与积压消退。网络注入限定于测试进程或独立网络命名空间，并记录还原结果。

600 ms 停顿期间会缺少新画面。恢复验收从新数据重新到达时开始，检查是否快速回到当前画面，以及一次停顿是否触发连续降档。

## 7. 阶段 P3 —— 按实测处理剩余瓶颈

### 7.1 网络路径检查与分组

复测时先确定当轮 Tailscale direct / DERP、实际端点、RTT、最长到达空档与带宽余量。本次文档编写没有执行新的网络探测，历史路径作为条件记录使用。

只读路径检查可使用以下命令，Linux 对称执行到 Windows 地址的检查。

```powershell
& 'C:\Program Files\Tailscale\tailscale.exe' ping -c 3 100.87.60.58
& 'C:\Program Files\Tailscale\tailscale.exe' netcheck
```

保存 UDP 可达性、端点映射变化、端口映射和 DERP 探测结果。把路径结果与实际传输事件关联。映射变化可作为 NAT 行为线索，具体原因继续用端点、路由与规则证据核实。

需要调查直连问题时，按下列顺序收集证据。

1. 保存双端 `tailscale status`、ping 和 netcheck 结果，带时间与软件版本。
2. 核对实际路由、接口 MTU、UDP 端点与防火墙规则。
3. 若存在 VPN、TUN 或过滤驱动，检查目标流量实际经过的接口及进程路径。
4. 有路由器访问条件时，核对 NAT 与端口映射的当前状态。
5. 对定位出的因素做单变量实验，记录恢复步骤与原值。

若网络调整获得更低 RTT 的路径，先在新路径重建 400 ms 基线，再开展缓冲对照。报告分别量化路径变化和应用参数变化的收益。

中继条件下持续观察修复成功率与拥塞反馈时效。direct 稳定性同样由连续运行和实际画面表现验证。

### 7.2 发送排队与关键帧

分析 `pacedBytes`、编码输出大小、关键帧大小、GCC 估计与真实收发字节的同一时间线。将 `pacedBytes × 8 / 当前估计码率` 作为队列等待估计，标注估计误差。码率变化、重传和探针计数口径分别核对。

已有编码前丢帧保护、单帧队列和 MTU 配置在基线中复验。新增参数实验一次调整一个变量，优先处理已证明的排队增长。预算控制的验证同时包含 RTP / 修复 / 加密开销和关键帧突发。

### 7.3 控制消息与文件竞争

用 S4 比较空闲与复制文件期间的输入回执和画面反馈 p95 / p99。若文件场景出现明确排队，先给文件发送增加受控背压和控制消息优先调度，再评估独立 DataChannel。

拆分通道时验证授权、按下 / 松开顺序、撤销、代次与断线清理。即使使用不同 DataChannel，SCTP 连接和网络带宽仍需联合观察。此项以文件竞争的真实证据作为实施入口。

### 7.4 编解码与图像拷贝

用现有分段耗时判断 CPU、转换和拷贝是否占主要延迟。建议的调查触发值为编码 p95 超过 12 ms，或解码加颜色转换 p95 超过 8 ms，持续至少 30 秒。触发值属于调查门槛，需结合帧预算与设备状态解释。

确认瓶颈后再比较 VP9 硬件路径或其他低延迟编码候选。对照必须覆盖跨平台兼容、4:2:0 细字画质、启动、重开、分辨率切换、丢包恢复和软件回退。

若实测瓶颈需要进入硬件候选阶段，需分别处理当前两处实现。

- 发送端 `selectEncoder()` 在 `lowBandwidth_` 为真时直接选择软件编码，见 [编码选择](F:/projects/ZJdesk/src/media/screen_share.cpp:989)。硬件候选需同时验证 WAN 码率控制与 I420 输出要求。
- 接收端使用 `vp9dec`，见 [接收管线](F:/projects/ZJdesk/src/media/screen_share.cpp:233)。硬解候选需验证具体设备、驱动、VP9 profile 0 支持及输出格式。

现有硬件编码分支使用 `VUYA` 输入，见 [硬件编码管线](F:/projects/ZJdesk/src/media/screen_share.cpp:971)。WAN 候选需要检查 `vavp9lpenc` 对 I420 / NV12 的实际协商能力，再比较同一画面、码率、画质与修复条件下的收益。

## 8. 建议验收门槛

以下阈值用于立项和比较候选，尚未由本项目新一轮数据验证。阶段 P0 建立基线后可以调整，调整须记录依据，并同时列出调整前后的结果。

| 维度 | 建议门槛 | 失败处理 |
| --- | --- | --- |
| 分辨率与目标档位 | 稳态样本全程 1920×1080 / 30 | 发生降档即记录该轮未通过保持目标档位 |
| 实际 FPS | 加权平均 ≥28.5，1 秒窗口 p50 ≥29，至少 95% 窗口 ≥27 | 分开分析编码、交付和实际绘制 |
| 反馈延迟改善 | 相邻 400 ms 基线相比，p50 至少降低 100 ms、p95 至少降低 80 ms | 缺少闭环测量时该项待验收 |
| 延迟尾部 | p99 相对配对基线增加 ≤50 ms，超时比例 ≤0.5% | 原样记录长尾与超时 |
| 稳态呈现间隔 | p99 ≤100 ms，最大 ≤250 ms | 当前网络若达不到，明确标注路径受限 |
| 故障恢复 | 600 ms 专用停顿结束后，1 秒内恢复新画面，2 秒内消退额外积压 | 保留故障全过程与退化原因 |
| 画质 | 既有画质回归通过，提交匹配画面位置与内容的基线对照 | 对细字、彩线、滚动分别给出证据 |
| 连续运行 | 每方向连续 30 分钟通过，再扩到 60 分钟 | 日志覆盖率 ≥99%，缺失段单列 |
| 资源 | 无持续内存或队列增长，CPU / GPU 有稳定余量 | 跟踪进程与队列时间序列 |
| 输入安全 | 授权、撤销、松键、松鼠标和断线清理回归通过 | 修复后重新执行相关回归 |

全部真实运行窗口进入汇总。故障注入样本独立成组，正常链路样本的自然停顿完整保留。单次热点波动会影响配对结果，候选决定至少基于 3 组相邻对照。

Linux 接收侧拥有真实后台 OpenGL 呈现证据后，才填写双向实际绘制验收。此前可以分别填写“Windows 绘制通过”和“Linux 解码交付通过”。

## 11. 回退方法

固定缓冲候选出现实际绘制恶化、明显长尾或恢复失败时，在接收进程显式设置 `ZJDESK_WEBRTC_LATENCY_MS=400`，重新建立共享会话，并核对实际读回值。

拟实现的自适应控制应保留固定档覆盖。运行期调整失败时记录失败原因与最后一次确认生效的档位，按验证过的路径恢复。若恢复需要重建共享，会话协调层负责状态与授权清理。

最终报告列出默认值、候选值、回退触发条件、操作方法和恢复验证。部署产物附提交号及运行库版本，确保测试构建和交付构建一致。
